# Mocha concurrent map

This is a locally maintained derivative of [Papaya 0.2.4](https://crates.io/crates/papaya/0.2.4), by Ibraheem Ahmed, distributed under the MIT license in `LICENSE-MIT`. `raw/` retains its concurrent storage, incremental migration and Seize reclamation algorithms, with the waiting changes described below and the unused blocking resize mode removed. `mod.rs` provides the smaller API used by Mocha; `raw::HashMap::scan` and the scan tests are local additions. The production dependency on the Papaya crate is removed; the original crate is a dev dependency for comparison benchmarks.

The entry/slot representation stays the same. Each slot has one byte of metadata and one atomic pointer, and each entry contains only its key and value. SCAN adds no second key index, cached full hash, per-client cursor state, global scan lock or bookkeeping in point reads/writes. Compute candidate ownership is managed separately on the operation's stack, as described in the regression-suite section. Retaining the atomic write paths is necessary: in addition to serial Raft writes, Mocha's expiration worker and lazy deletion physically mutate the map from other threads.

## Cursor traversal

A cursor identifies a **logical home bucket** (`hash & mask`), not a physical probe slot. Each page completes the quadratic probe sequence for a selected home bucket, selecting only entries with that home hash. It then advances the 64-bit cursor in bit-reversed order. Powers-of-two table growth splits a home bucket into consecutive positions in this order; shrinking can revisit already scanned keys but cannot skip keys that remain present throughout a complete iteration. Same-size tombstone cleanup leaves logical bucket membership unchanged.

A call pins the root and captures the existing successor-chain frontier. For every selected root home bucket it visits the corresponding buckets of those tables. Larger successors split the bucket; smaller successors merge it, so candidates are filtered against both masks. Copying preserves source pointers until guards leave. If a candidate has been copied, a current lookup resolves replacement/deletion, so an old copy of a key deleted before this call is not returned. Entries first added during an iteration may or may not appear; repeats during migration are allowed, as in Redis. No client may rely on uniqueness.

The frontier is fixed before callbacks run, preventing a callback or later resize from extending the page's bucket traversal. Frontier discovery and current lookups have the same lock-free (not wait-free) progress qualification as the inherited table: an adversarial stream of concurrent resizes can delay them. SCAN does not help complete a whole-table resize. In a single table, a page visits at most `10 * COUNT` logical buckets and at most `min(capacity, 1 + probe_limit)` slots per bucket. Collision groups are never split and may exceed COUNT. Sparse maps and post-filtering may produce empty pages with nonzero cursors.

Empty maps finish with cursor zero, including after FLUSHDB. A null root finishes immediately. For allocated tables, a zero length counter is only a hint: publication and sharded counter updates are separate, so concurrent writers can temporarily report zero while a stable key still exists. SCAN confirms emptiness by checking the captured physical tables and resolving copied candidates. This exceptional empty check costs O(allocated slots), adds no point-operation bookkeeping, and falls back to normal paging if a live candidate exists.

SCAN hashes candidate keys to recover their home bucket. This costs more than ordinary linear iteration, especially for long keys and crowded/tombstone-heavy tables, but adds no storage or point-operation overhead. Snapshot iteration remains the original duplicate-free physical iterator, including its existing migration completion behavior; it does not use SCAN. The existing snapshot revision/delta protocol still provides state-machine snapshot semantics.

## Lifetimes and verification

Local and owned Seize guards keep table and entry pointers alive. Owned guards support asynchronous snapshot I/O. Holding either kind for a long time retains retired storage, just as in Papaya. Cursor values do not hold guards and require no cleanup; restart, snapshot installation and leader changes require restarting with cursor zero.

`tests.rs` exercises collision groups, tombstone predecessor deletion, forced incremental growth/shrink/cleanup, successor-only insertions, stale copies, replacement values, sparse/count behavior, arbitrary cursors, concurrent readers/writes and guard reclamation. Test-only resize hooks live in `raw/mod.rs` and are absent from production builds. `cache_cat/examples/mocha_map_bench.rs` compares identical hash seeds and payloads against Papaya, including requested allocation bytes and peak allocations. Measurements are container benchmarks, not whole-server throughput or RSS guarantees.

## Waiting and allocation

GET and ordinary writes outside migration do not take map mutexes. When a copied entry or table promotion is incomplete, a waiter uses `parking_lot_core`'s shared address queues. Each table keeps only an atomic pending-waiter count, replacing the previous mutex and nested hash maps of thread handles. With no waiters, publishing a copied entry checks the count and returns without touching a queue lock. An already completed condition also returns before registering a waiter. Queue locks exist only on the contended waiting path; this is not a claim that all map operations are lock-free.

Waiter registration, completion publication and the no-waiter check retain their SeqCst ordering. Queue-locked validation compares primitive atomic values; user predicates execute outside the queue lock. The atomic trait is sealed to pointer and byte atomics. RAII unregisters a waiter on return or predicate panic, and a Seize guard keeps the address alive throughout waiting. Tests cover wake-before-registration, wake-before-validation, multiple keys/waiters, panic cleanup and a copier deliberately suspended while updates, removals and compute calls wait.

Successor allocation retains a `parking_lot::Mutex<()>`: concurrent expiration or snapshot helpers can reach this path, and allocating competing large tables before a CAS would increase memory pressure. The lock is not taken for every write. The inaccessible blocking resize mode and its branches have been removed; the default migration batch remains 64 slots. Bulk iteration/clear still explicitly complete pending migration when needed, while SCAN never does. `cache_cat/examples/mocha_lock_bench.rs` measures growth, churn, reads and auxiliary expiration with latency percentiles and allocation accounting; results and qualifications are in `docs/mocha_lock_optimization.md`.

## Correctness regression suite

The map suite contains 48 tests. Alongside the original cursor and parking cases, `tests/model.rs` compares 44,800 seeded mixed operations against a standard HashMap, including collision groups, returned values, Compute outcomes, borrowed keys and changing scan counts. Failures retain the seed, step and recent actions. `tests/concurrency.rs` checks unique atomic-increment results, stale conditional deletion after replacement/recreation, exact final states, and 32 short histories against an independent sequential specification with real-time ordering constraints.

`tests/scan.rs` tests every page boundary across partial growth/shrink/cleanup, multiple unfinished successor tables, independently interleaved cursors, and removing an entry from its own visitor. `tests/lifecycle.rs` checks non-Clone keys/values are destroyed exactly once, owned guards/iterators moving between threads, and callback/hash/destructor panic boundaries. Tests coordinate races with channels and barriers rather than relying on sleeps for correctness.

Those tests exposed an inherited Papaya 0.2.4 leak: after a lost compute CAS, a later callback panic leaked the unpublished key allocation. Compute candidates now own their key, allocation and initialized value through a local RAII state until successful publication. CAS success transfers ownership before old-value retirement or callback destruction can unwind; retry caching transfers the value out before replacing cached state. This adds no stored node/table fields or allocations. Tests also ensure a destructor panic after successful publication cannot reclaim a live entry.

Run the suite with `cargo test -p cache_cat --lib mocha::map` (add `--release` to test optimized code). The task's isolated harness under `target/mocha-map-probe` compiles these same source files without rebuilding the rest of the server. Debug and Release results, repeated concurrent runs and the existing unrelated full-suite failure are recorded in `docs/mocha_lock_optimization.md`.
