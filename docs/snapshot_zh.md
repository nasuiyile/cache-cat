# 快照逻辑

## 常见的快照策略

Consul，使用go-memdb进行存储，其实现了内存mvcc机制。Zookeeper，将所有操作变成CAS操作，因此后续的请求可以被应用多次，从而达到相同的数据逻辑。

Dragonflydb，通过任期手动标识哪些数据是旧的哪些数据是新的，执行完快照逻辑后手动收集变动部分数据。ETCD，通过存储层的数据库（BoltDB）来直接实现MVCC快照。Redis
通过linux下的fork指令（linux的fork会复制整个进程的地址空间，但只复制调用fork的那个线程）。

然而以上数据结构都存在特定的问题。Consul，Zookeeper，ETCD 只支持非常单一且特定的数据结构。
Kvrocks，pikiwidb，Tendis均采用Rocksdb，直接使用Rocksdb的MVCC机制来实现快照隔离。
而Redis的fork存在问题，当快照期间遇到大规模的数据写入时，fork操作会产生大量的内存占用。这是因为fork虽然是COW的，但是每一个值的修改，都会导致完整的内存页进行一次复制（在x64系统下通常是4kb）。并且只要父进程持续写入，就会不停的发生页复制，如果磁盘性能不够强会导致snapshot花费很久时间加剧了页复制的情况。
此外fork操作还会造成一个短暂的STW停顿，主进程在内核中执行fork的一段时间无法处理对外的客户端请求。生产上为了减小fork的影响，会限制Redis的容量上限。

Dragonflydb避免了fork操作。https://www.dragonflydb.io/docs/managing-dragonfly/snapshotting
。但引入了新的问题，https://github.com/dragonflydb/dragonfly/issues/6578 。
Dragonflydb为hashmap定制了一个通用的快照策略，因此能兼容Redis的所有数据结构。然而，当map中的一个key的value是一个较大的值时，由于读写操作不能同时访问该key，从而导致对该键值对进行快照会消耗较长的时间。
Dragonflydb内部使用了一个fiber，这个fiber只能自己放弃cpu或者任务出现阻塞才会产生切换。（fork和主行线程其实都是一个线程）
试想你将Dragonflydb的List结构用作消息队列。当某个key的value有几十G时，此时进行快照会长时间对该键值对进行占用，写入操作只能在原地等待直到对于该键值对的快照完成。这是由于Dragonflydb目前没有为所有的数据结构提供专属的快照策略导致的。
仅针对于Hashmap的读写并发结构的设计是相对简单的。但当Hashmap的value为各种不同的如链表，Skiplist等数据结构时，设计的复杂度会变得非常高。

此外Dragonfly的策略会让快照期间正在写入的线程去序列化数据的（这增加了延迟）。并且每次这个序列化操作都是直接序列化key下的整个value。因此Dragonflydb中不能在value中存放大尺寸的数据。

在没有MVCC，不采用Fork指令的情况下，只有Dragonflydb的策略和Zookeeper的策略可以被参考。下文对比俩方的缺点。默认Zookeeper是让每个指令进行CAS操作，我们这里假设只在快照的期间记录版本号。

Dragonflydb的缺点

- 当快照线程还没有来得及序列化数据的时候，每次产生的写操作都会导致先进行阻塞，完成序列化发送给落盘线程。带来了潜在的延迟变高。
- 由于默认是将数据统一先序列化，然后发送快照线程，会带来额外的内存占用（并且在理论上就无法存放过大的value值，比如当单个List中有数十G的value）。即便这些内存在写入完毕后就会被释放。Zookeeper可以一边遍历一边写入磁盘。

Zookeeper方案缺点(下文方案)

- 每个 value 的快照版本号需要写入快照。Cache-cat 在内存和磁盘中均使用 u64 版本号。
- 在快照安装时，需要对每一条写入操作的指令实现对应的CAS操作，这会大大增加适配的复杂度。
- 无法和兼容Redis的快照格式。
- 快照构建时，所有数据都需要被缓存起来。此时所有的请求都会带来翻倍内存占用（Zookeeper自身的共识算法能避免这个问题）。

## 快照策略

> 下文是Cache-cat原创的快照策略，总思想类似Zookeeper，将所有操作变成一个CAS操作。对应Dragonfly中的Relaxed快照策略。Zookeeper方案有个缺点，RAFT的快照中的快照语义需要是一个时刻的瞬时快照。

其中map中的每个value都可以被试做为一个原子访问单元。对这个value的任何操作都是原子的，且读写并发的。

`meta_data` 包含 `last_applied_log_id`、`last_membership`、`snapshot_state` 和 `snapshot_revision: u64`，由状态机已有的互斥锁保护。每个 value 维护一个 u64 快照版本号。`Start` 以外的普通写入使用基线版本 0；`Start` 期间成功修改数据时，从节点本地的单调计数器分配非零版本。此计数器跨数据库、跨多次快照连续分配，删除或过期不重置它。版本号禁止回绕，u64::MAX 保留不用。

Raft 的日志应用串行执行，每批操作已经持有 `meta_data` 锁，因此通过 `&mut u64` 将计数器直接借给执行上下文即可，无需原子变量或额外加锁。快照线程在同一个锁内读取高水位。计数器不能在每批操作或每次快照开始时归零；批次中途出错或快照失败时，也必须保留已分配的版本。

每条增量记录包含 `expected_revision: OptionalU64`、`version: u64`、具体操作、数据库编号和写逻辑时钟。`OptionalU64` 用 u64::MAX 表示不存在，在内存中和序列化后都只占 8 字节。`Some(0)` 表示存在的基线版本，和键不存在有明确区别。`version` 是本次操作的唯一版本；如果执行后仍有 value，就作为它的新版本。删除语义已经包含在操作中，因此无需第二个可空字段。

**业务线程**

1. 当有一批新的操作到来。通过锁获取meta_data。
2. 更新last_applied_log_id
3. 如果当前 snapshot 状态为 `End`，正常执行操作。此路径写入的 value 使用基线版本 0，不递增快照计数器。
4. 如果当前 snapshot 状态为 `Start`，记录执行前的版本或不存在状态，执行操作，并为成功的修改分配新版本。如果执行后存在 value，就赋予它此版本；将预期版本、新版本和操作写入队列。未修改数据的指令无需记录增量。清库操作即使作用于空库也分配版本。
5. 如果当前snapshot状态为`Tail`，直接按正常流程应用该Raft日志，不再写入快照增量队列。该日志位于快照记录的`last_applied_log_id`之后，恢复时由Raft日志补上。

**快照线程**

获取meta_data的锁，将快照标记为`Start`，然后释放锁。此时记录快照状态，但最终的`last_applied_log_id`在进入`Tail`时确定。

进行快照操作迭代所有数据，将数据写入磁盘中。

快照状态分为三个阶段：

- `Start`：快照线程正在遍历全量数据。业务线程应用的写入同时更新内存，并将操作、预期版本或不存在状态、新版本、数据库编号和写逻辑时钟放入增量队列。
- `Tail`：全量数据遍历完成。快照线程获取 `meta_data` 锁，在这个锁保护下将状态切换为 `Tail`，原子地取出并清空 `Start` 阶段积累的增量队列，并记录此时的 `last_applied_log_id`。从切换到 `Tail` 开始，新的 Raft 日志不再进入快照增量队列，而是按正常流程应用；这些日志的编号位于快照记录的 `last_applied_log_id` 之后，恢复时由 Raft 日志继续补齐。
- `End`：增量队列已经写入快照文件，文件完成刷盘并替换当前快照文件后，状态切换为 `End`。

`Tail` 阶段的队列排空和状态切换必须在同一个 `meta_data` 锁保护下完成，避免有操作在队列排空后又被错误地加入快照队列。`Tail` 阶段产生的 Raft 日志可以与快照文件的刷盘并发进行，但不能被当作快照增量队列处理。

在同一个锁内，还要保存最终写逻辑时钟和版本计数器的高水位。高水位必须独立保存：最大的版本可能来自删除或清库，不会留在任何 value 中。启动加载及安装快照时，都要先恢复高水位，再允许分配新版本。快照文件格式升级为 2，不兼容旧的 alpha 版快照。

**恢复操作**
读取全量数据，恢复到状态机。（这时暂停对外访问）
严格按原顺序回放增量队列。对于单键操作，只有当前版本与 `expected_revision` 精确匹配时才执行，包括对键存在与不存在的区分。如果产生 value，就赋予记录中的 `version`；否则删除键。版本不匹配表示全量扫描已经捕获了另一时刻的状态，应跳过此操作。

仅比较版本大小，或者“键不存在就执行”，都不充分。例如原有的带 TTL 键执行 `INCR` 后会保留 TTL；如果全量扫描后来已经看不到这个过期键，恢复时在空键上执行 `INCR` 会创建值为 1 的永久键。保存原来的存在状态可以阻止这种错误复活。

快照中的 `last_applied_log_id` 是进入 `Tail` 时记录的日志位置。安装快照后，首先按 CAS 顺序回放 `Start` 阶段保存的增量队列；随后由 Raft 继续应用该日志位置之后的日志，这些日志对应 `Tail` 阶段及之后的写入。

为什么这样是对的？快照线程和业务线程是并发的。因此快照线程在执行快照的时候会保存俩种快照数据，旧的和新的（每条数据都是原子的）。
当快照开始的时候业务线程执行的所有操作会被存下来到队列中，保存下来的所有队列元素都是带版本号的CAS操作。
因此在恢复快照的时候，只需要将快照数据恢复+队列中的数据进行CAS，最终得到的就是正确的最新数据。
快照线程在开始和结束的时候都会短暂的对状态机进行加锁，最终完整被还原后的数据是第二次加锁时内存中的数据。因此这种快照策略通常被视为后快照策略。

## 多key操作
上述操作依然不能解决一个问题，当遇到 SINTERSTORE ，SUNIONSTORE我们无法保证读取的一批key都是同一版本的。
现在A数据 版本v1，B版本v1
1. 快照了记录B v1
2. 你读取A和B，并修改了C（然后放进执行队列中）
3. 后续的写修改了A  v2
4. 快照记录A v2。

这时候如果快照直接重放你的操作，会发现当前操作依赖的俩个版本都不是当前执行的版本了.

因此对于这类命令，在快照逻辑上会把其看作多条命令，对于raft来说，仍然是单条命令，来保证命令的原子性。但是对于快照来说，需要将多条命令看作一条命令，来保证快照的原子性。

读取多键、写入单键的命令，记录已经计算好的目标键写入，恢复时不重新读取源键。多键写入按原执行顺序记录各个键的操作。

`FLUSHDB` 和 `FLUSHALL` 恢复时需要使用版本界限，只删除版本小于该次清库版本的 value。全量快照可能已包含清库之后的新写入，这些值必须保留。这个遍历只发生在快照恢复期间；正常清库仍直接清空数据库。

## 本地版本号与 Raft

快照版本号是节点本地的辅助信息，不加入普通 Raft 请求，也不随每条日志复制。各节点可以在不同时间构建快照、产生不同的版本号，但必须得到相同的 Redis 数据、TTL 和响应。只有快照文件向其他节点传输 value 版本、增量记录以及计数器高水位。安装快照后，后续 Raft 日志仍走正常执行路径。快照 `Start` 以外的普通读写不增加版本计数器操作。

## 读写逻辑时钟兼容

> 问题：当一个操作被被push到队列时，如何知道pair+当前操作后的结果？ 如果主节点执行该操作，可能在key过期之前来执行，也可能在key没有过期的时候来执行。

当快照开始后，每一条操作的进行都会被push到操作队列中，并且将生成的写逻辑时钟，push到队列中（这个写逻辑时钟是已经计算完`max(写逻辑时钟，读逻辑时钟，当前时间戳)`之后确定性的结果）。

**恢复快照**

先暂停过期工作线程，将写逻辑时钟置为 0，再加载全量数据。之后按增量队列记录的逻辑时钟回放操作；回放结束后发布快照保存的最终写逻辑时钟，恢复过期线程。这样也能正确处理没有修改数据、因而没有增量记录的命令所推进的时钟。

之后还原的时候先还原写队列中的逻辑时钟，然后直接apply这个操作序列。写逻辑时钟是操作队列，并且每个操作都是确定性的。当apply第一条队列中的日志时，写逻辑时间戳将会被更新。这时数据开始走正常的过期逻辑。每个操作执行完毕后，哪些数据应该被过期都是确定性的。

日志apply的顺序依旧和主节点是一样的，只不过如果发现版本不对就不会实际修改数据。

我们记录的操作队列是有序的，因此在恢复快照的时候，只需要将快照数据恢复+队列中的数据进行CAS，最终得到的就是正确最新的数据。

最后快照完毕时，也会将当前节点的元数据以及写逻辑时间戳加锁后保存。
