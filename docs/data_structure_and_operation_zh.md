# 数据结构设计

## 数据结构文档

> 简单起见，使用Redis的基础数据结构作为标题。大部分操作还处于适配开发阶段。

### String

所有数据结构的外层 key-value 操作使用 `mocha::map::HashMap`，`mocha::Mocha` 在其上包装逻辑时钟和时间轮过期。底层是从 Papaya 0.2.4 派生的本地并发表，代码位于 `cache_cat/src/mocha/map`，生产路径不再依赖 Papaya crate；原 crate 仅作为基准测试对照。保留原有的原子发布、渐进扩容和 Seize 内存回收机制，兼容串行 Raft 写入、并发读取、后台过期及惰性删除。

`SCAN cursor [MATCH pattern] [COUNT count] [TYPE type]` 实现 `MultiReadCommand`，通过数据库遍历接口直接访问候选项，不构建全库键列表或克隆 value。游标按键哈希的逻辑桶进行位反转遍历；每次完整扫描选中桶的二次探测序列，并覆盖正在迁移的后继表对应桶，因此扩缩容、同容量重建及其他键的增删不会漏掉完整扫描期间始终存在的键。迁移时允许重复键。COUNT 默认 10，在过期、MATCH、TYPE 过滤之前计数；每批最多选择 `10 * COUNT` 个根表逻辑桶，碰撞组不拆分，允许超出 COUNT 或返回空结果和非零游标。过滤使用固定读/写逻辑时钟，TYPE 与已有 TYPE 命令共用类型名称；未知类型合法但不匹配。

SCAN 不保存服务端会话、不增加第二份键索引或条目字段，也不让普通 GET/SET 额外加锁。扫描时重新计算候选键哈希，复制过的旧条目通过当前查询确认，因此扫描速度低于普通线性迭代；渐进迁移期间可能访问多张表。单表中每桶最多检查 `min(容量, 1 + 探测上限)` 个槽。前沿发现和复制条目的查询保留底层无锁但非 wait-free 的进展性质。普通快照仍使用原有无重复物理迭代器及版本/增量协议，不使用 SCAN。

Lua/EXEC 中返回全部匹配键的字节序排序结果及游标 0，避免节点本地哈希布局影响后续写入，复杂度为 O(N + M log M)。普通读取不做全库排序。重启、安装快照或切换主节点后客户端需从游标 0 重新扫描。容器内存和常用操作的对照见 `cache_cat/examples/mocha_map_bench.rs`，算法与继承代码说明见 `cache_cat/src/mocha/map/README.md`。

空库（包括 FLUSHDB 后）直接返回游标 0。已分配的表不能仅凭并发分片计数为 0 判断为空：该提示会触发槽位验证，并对复制条目查询当前状态，防止短暂零计数造成漏键。此空表验证遍历已分配槽位，不受 COUNT 限制；成本局限于 SCAN，不增加普通读写的计数操作。验证记录及基准方法见 `docs/mocha_lock_optimization.md`。

扩容只保留渐进式模式，默认每批迁移 64 槽。等待复制或发布完成时，使用共享的按地址停车队列，表内只保留原子等待计数，移除了每表等待登记 Mutex 和两层 HashMap。无人等待时不访问队列锁。分配后继表仍由紧凑的 `parking_lot::Mutex<()>` 保护，避免并发帮助线程重复分配大表；普通查找和未遇到迁移的点写不取得这把锁。

### Hash

Hash 的字段容器使用 `ScanMap<Bytes, HashValue>`，外层保留 `Arc<Mutex<_>>`。条目连续存放，桶链保存条目索引和缓存的哈希值，不为每个字段单独分配节点。支持已有 Hash 命令所使用的查找、插入、删除、遍历、克隆和序列化 API；ZSET 的成员索引也复用 ScanMap（见下文），外层 mocha 保持原有容器。

桶数为 2 的幂，负载因子上限为 0.5，仅桶数组保持较低负载，不额外翻倍分配条目数组。采用带随机密钥的 `ahash::RandomState`；每个桶维护轻量哈希标记，在大多数未命中查询中避免访问条目数组。删除时同步更新标记，避免长期增删使过滤能力退化。扩容一次性重建桶链，不采用渐进式迁移，也不在删除时自动缩容。删除通过交换尾部条目保持存储紧凑，并修复桶链；普通遍历与字段数量成正比。扩容仍会持有该 Hash 的互斥锁，并可能延迟串行 Raft 写入。

Redis Hash 写命令将稠密字段数组的顺序作为复制状态：新字段按参数顺序追加，更新保留位置，HDEL 将尾字段交换到删除位置。克隆、重建桶索引以及快照序列化和恢复均保留字段顺序，哈希种子和桶布局仍属于节点本地信息。Hash 命令不使用 ScanMap 中顺序依赖容量的通用 retain；未来新增过滤写入必须确保各副本字段顺序一致。HGETALL、HVALS 在普通读取和 Lua/EXEC 中均直接遍历稠密字段数组，复杂度 O(N)，无需排序；字段和值保持对应，HVALS 保留重复值。

HRANDFIELD 直接按字段数组下标读取，与 SRANDMEMBER 共用只读下标采样。单个采样为 O(1)，不创建辅助集合；正 count 返回不重复字段，k 截断到字段数量后，预期时间为 O(k)：少量采样使用稀疏的虚拟 Fisher-Yates 映射，较多采样使用长度不超过 4k 的临时下标数组，请求全部字段时直接返回稠密顺序。负 count 有放回采样，复杂度 O(abs(count))，只复制返回的字段和值。普通请求使用线程本地随机源，Lua/EXEC 根据复制的逻辑时钟和 key 初始化固定算法的随机数生成器。采样（包括 WITHVALUES）不修改字段顺序、值、TTL 或快照版本。

`HSCAN key cursor [MATCH pattern] [COUNT count] [NOVALUES]` 通过 `ReadCommand` 执行。普通请求采用位反转游标，完整扫描每个选中的桶，因此扩容和其他字段的增删不会漏掉完整扫描期间始终存在的字段。`COUNT` 默认 10，是扫描工作量提示，计数发生在 `MATCH` 过滤之前；每批最多尝试 `10 * COUNT` 个桶，碰撞链不拆分，所以允许超出 COUNT，也允许空结果携带非零游标。游标为 0 表示开始或结束，不保存服务端会话状态。

Raft 中 Lua/EXEC 的扫描结果可能决定后续写入。由于各副本的随机种子和容量不同，该路径返回匹配字段的完整排序结果和游标 0，允许接受普通扫描产生的游标，并可能重复返回先前已经扫描的字段。该路径时间开销为 O(N + M log M)，N 为字段总数、M 为匹配数；普通 HSCAN 不做整表排序。快照仅序列化字段和值，恢复时重建索引和随机种子；普通游标不保证跨重启、快照安装或主节点切换继续有效，此时客户端应从 0 重新扫描。

`MEMORY USAGE` 按实际桶数组和条目数组的容量估算容器内存。`cache_cat/examples/hash_map_bench.rs` 提供与原标准 HashMap 的查找、更新、删除、插入和遍历对照测试。

### List

使用 `std::collections::LinkedList` 实现。读写并发可以用crossbeam SegQueue实现。

### Set

Set 使用 `ScanSet<Bytes>`，在 ScanMap 上提供集合接口，值为零大小的 `()`，外层保留 `Arc<Mutex<_>>`。Set 在编译期选择最高 0.75 的桶负载，Hash/ZSET 保持原有 0.5 配置。增删、成员查询、稠密遍历和桶游标复用 ScanMap；Set 的 `retain` 无论本地容量如何，均按相同顺序交换尾部条目删除：稠密表在过滤后原地重建桶链，稀疏表逐项修复删除以避免遍历大量空桶。两种路径均复用缓存哈希，不分配临时集合，并在异常退出时保持索引有效。Hash/ZSET 保留已有过滤行为。集合运算的写入目标直接构建 ScanSet；纯读 SINTER/SDIFF 使用成员数组过滤，避免复制和维护临时桶索引。

稠密成员数组的顺序属于 Set 的复制状态。新成员按命令参数顺序追加，已有成员保持位置，删除时将尾成员移到被删除的位置。集合运算按源键参数顺序和源成员数组顺序构建结果，过滤后的顺序不能依赖节点本地哈希种子或容量。重建桶索引和快照克隆均保留成员顺序；全量快照和已计算的目标键写入按此顺序序列化成员，恢复时按相同顺序插入。哈希种子、缓存哈希、桶链和分配容量仍是节点本地信息，由恢复端重建。

`SPOP` 实现 `ComputeCommand`，使用 key 和随日志复制的写逻辑时钟初始化已有确定性随机数生成器，直接对稠密成员数组采样。按采样下标交换尾成员删除，并用缓存哈希修复桶链，无需收集或排序整个集合。返回 k 个成员时，普通执行路径的预期时间为 O(k)，响应空间为 O(k)；哈希碰撞仍保留通常的最坏情况限制。不新增成员字段、索引或锁。快照 `Start` 阶段写入前已有的整容器克隆仍有 O(N) 成本。复制测试需要比较成员数组顺序和后续 SPOP 响应（包括快照恢复后），不能仅比较集合成员是否相同。

SMEMBERS 在普通读取和 Lua/EXEC 中均直接按稠密成员顺序返回，复杂度 O(N)，无需排序。SRANDMEMBER 与 HRANDFIELD 共用只读下标采样：单成员为 O(1)，正 count 截断到集合大小后预期为 O(k)，允许重复的负 count 为 O(abs(count))；少量采样不构建全量成员数组。普通请求使用线程本地随机源，复制读取用 key 和逻辑时钟初始化固定算法的随机数生成器。采样只使用临时下标映射，不修改 Set 或成员顺序。这五个读取命令（SMEMBERS、SRANDMEMBER、HRANDFIELD、HGETALL、HVALS）的确定性依赖一致的修改历史和保留的数组顺序，不要求本地哈希布局相同，也不需要按字节排序响应。

`SSCAN key cursor [MATCH pattern] [COUNT count]` 使用 `ReadCommand`。普通读取采用位反转桶游标，COUNT 默认 10，在 MATCH 过滤前计数，每次最多尝试 `10 * COUNT` 个桶，碰撞链不拆分。允许超出 COUNT，也允许空结果携带非零游标。扩容以及其他成员的增删不会遗漏完整扫描期间始终存在的成员；RESP2/RESP3 均返回 `[cursor, [member, ...]]` 数组。

Lua/EXEC 中返回按成员字节排序的全部匹配成员和游标 0，避免副本本地哈希种子及容量不同影响后续写入。该路径开销为 O(N + M log M)，普通读取不执行全量排序。快照期间的容器克隆保留哈希种子，并为下一次写入保留适量条目容量，避免克隆后单成员 SADD 再次搬移整张表。桶数超过成员数八倍时，克隆按缓存哈希重建较小的桶数组。位反转游标支持同步扩缩容：缩容允许重复返回已扫描成员，但不会遗漏完整扫描期间始终存在的成员；快照仅持久化成员序列，恢复时重新建表，重启、快照安装或主节点切换后客户端应从 0 重新扫描。

`MEMORY USAGE` 按实际桶和条目数组容量估算。Set 的桶负载上限为 0.75，每个条目及桶也有额外索引元数据，`()` 零大小不表示容器成本与标准 HashSet 相同。同步扩容仍可能延迟串行 Raft 写入。`cache_cat/examples/set_bench.rs` 提供标准 HashSet 与 ScanSet 的常用读写、遍历、retain、克隆、克隆后写入和内存对照。基准支持基数、操作和成员长度筛选，以固定样本内哈希种子、交替运行顺序及最小累计计时降低噪声；结果为容器微基准，不代表完整 Raft 请求延迟。

### Sorted Set

ZSET 使用按 `(score, member)` 排序的带排名索引跳表，加上 `ScanMap<Bytes, f64>` 哈希索引，支持成员查找和游标扫描。每个跳表节点保存一小块有序成员，减少依赖访存和内存分配；每层链接维护按成员数计算的跨度，底层维护反向链接。节点使用稳定的 arena 索引并复用删除后的槽位，最多 32 层，逐层晋升概率为 1/4。块满时分裂，删除后空间允许时合并相邻块；分数更新未移出原块时复用已有分配。两个索引仍由现有 value 互斥锁保护，无需新增锁。

`ZRANK`、`ZREVRANK`、`ZCOUNT` 的期望时间复杂度为 O(log N)。按排名和分数的范围查询通过跨度定位边界，再遍历返回成员，期望为 O(log N + M)，包含反向查询和大 LIMIT 偏移。BYLEX 在所有成员同分这一 Redis 定义的场景下也通过索引定位；混合分数时保留原来的确定性过滤行为，可能全量遍历。成员查找仍为期望 O(1)，插入和删除为期望 O(log N)。

`ZSCAN key cursor [MATCH pattern] [COUNT count]` 使用 `ReadCommand`，基于哈希索引的位反转桶游标扫描。COUNT 默认 10，是 MATCH 过滤前的工作量提示；碰撞链保持完整，允许空结果携带非零游标。普通扫描不遍历或排序整个集合。扩容、其他成员的增删以及分数更新不会漏掉完整扫描期间始终存在的成员。响应包含游标和交替排列的成员、分数数组；RESP2 和 RESP3 的分数均使用 bulk string。

Raft 中执行的读取（Lua/EXEC）返回按成员字节排序的全部匹配项和游标 0，避免本地哈希种子、容量、跳表形状影响后续写入。此路径开销为 O(N + M log M)，普通读取不承担该成本。与 HSCAN 相同，重启、快照安装或主节点切换后，普通扫描应从游标 0 重新开始。

快照按分数、成员顺序仅序列化一次逻辑 `(member, score)`。恢复时逐条验证该顺序。对于编码声明超过 4096 个成员的集合，通过有界缓冲按顺序直接构建层链接、成员跨度和反向链接，并重建成员哈希索引，预期时间为 O(N)。构建保留普通顺序插入的布局：缓冲达到 65 个成员时，将前 32 个形成节点，其余继续作为尾部；完整节点及尾部沿用原来的预留容量，避免恢复后插入或合并增加重新分配。较小集合及未提供长度的编码保留逐项插入路径。初始预分配受限；恢复拒绝重复成员、NaN 分数及不符合分数、成员顺序的编码，正负零视为相同分数。这替换了之前 alpha 版本的 ZSET 编码。MEMORY USAGE 按哈希数组、跳表 arena 和层数组的实际分配估算内存，共享的成员 payload 只计算一次。`cache_cat/examples/zset_bench.rs` 对照原 BTreeSet + HashMap 实现测量查询及写入性能。 `cache_cat/examples/zset_restore_bench.rs` 测量快照解码和恢复后的读写性能。

### JSON

JSON 使用 `Arc<Mutex<JsonDocument>>`，内部直接存放 Redis 官方 `ijson` fork 的紧凑 `IValue`，不常驻第二份 JSON 文本或 `serde_json::Value`。上游版本和本地适配记录在 `vendor/ijson/UPSTREAM.md`。64 位平台的值句柄为 8 字节；短字符串内联，小对象按连续字段保存，同质数值数组使用紧凑元素。长字符串共享池在 JSON 内部同步，普通 Redis 类型不访问该池。

`JSON.GET key [INDENT indent] [NEWLINE newline] [SPACE space] [path ...]` 使用 `ReadCommand`。省略路径时采用 legacy 根路径 `.`；legacy 路径返回首个匹配值，`$` 路径返回匹配数组。多个路径返回以原路径为键的对象；混合 legacy 和 `$` 路径时，各项均为数组。格式化直接序列化借用的节点，不复制整份文档。`NOESCAPE` 为兼容选项，不关闭转义；RESP3 支持 `FORMAT STRING|EXPAND|EXPAND1`。

`JSON.SET key path json [NX|XX]` 使用 `ComputeCommand`，日志保存输入字节和选项，状态机直接解析为紧凑树。只允许在根路径创建新 key；局部更新可创建已有对象的最后一级字段，不自动补齐中间容器。已有 key 的 TTL 在根替换和局部更新后均保留。支持 `FORMAT JSON|STRING|BSON` 和显式的 `FPHA` 数值数组选项，默认不启用有损浮点精度。命令均可用于 EXEC 和 Lua。`TYPE`/`SCAN TYPE` 使用 Redis 的 `ReJSON-RL` 类型名称。

快照编码采用显式类型标签，直接通过 serde/bincode 流式编码树及数值数组，不依赖 `IValue` 的 `deserialize_any`。恢复校验深度、类型和数值，并保留对象字段顺序及数值数组精度。快照 `Start` 期间沿用现有 `snapshot_clone` 隔离：对象和数组会深克隆，长字符串共享；本实现不宣称分块 COW，也不保证大文档频繁更新时的低峰值。`MEMORY USAGE` 统计可达分配，跨 key 共享字符串和全局共享池使其与实际 RSS 存在差异。

## 读写并发模型

在Redis中有一个核心的执行队列，dispatcher，所有的命令都通过单线程执行。但在raft中这是不合适的，读命令和写命令的延迟差距较大。读命令通常可以在租约期内直接返回，写命令则要经过一轮完整的共识算法。此外raft核心执行也是单线程的。
自然而然的，cache-cat使用读写并发的Hashmap。

Rust的moka库已经保证了每个单key操作是原子的。读读之间显然是不冲突的。写写之间是串行的，因此也不会产生原子性问题。（这里的写包括了删除操作）

|                 | 单key写（多次） | 多key写 | 单key读 | 多key读 |
| --------------- | --------------- | ------- | ------- | ------- |
| 单key读（多次） | √               | x       | √       | √       |
| 多key读         | x               | x       | √       | √       |

当多key读遇到了多次的单key的写。比如这里执行mget读k1和k2：读取k1->写入k1->写入k2->读取k2。导致原子性出现问题，多key写同理。

当单key读取遇到了多key写：写k1->读取k1->读取k2->写k2，这里就读取到了中间状态。

Cache-cat中使用read_lock和write_lock来优化这个问题。

|                 | read_lock（RwLock） | write_lock（Mutex） |
| --------------- | ------------------- | ------------------- |
| 单key读（多次） | 读锁                | x                   |
| 多key读         | 读锁                | √                   |
| 单key写（多次） | x                   | √                   |
| 多key写         | 写锁                | √                   |

由于多key的读写是绝对的少数操作，只有多key操作下才会需要上俩把锁。
