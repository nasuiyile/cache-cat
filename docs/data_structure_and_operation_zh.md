# 数据结构设计

## 数据结构文档

> 简单起见，使用Redis的基础数据结构作为标题。大部分操作还处于适配开发阶段。

### String

所有数据结构的外层 key-value 操作使用 `mocha::map::HashMap`，`mocha::Mocha` 在其上包装逻辑时钟和时间轮过期。底层是从 Papaya 0.2.4 派生的本地并发表，代码位于 `cache_cat/src/mocha/map`，生产路径不再依赖 Papaya crate；原 crate 仅作为基准测试对照。保留原有的原子发布、渐进扩容和 Seize 内存回收机制，兼容串行 Raft 写入、并发读取、后台过期及惰性删除。

`SCAN cursor [MATCH pattern] [COUNT count] [TYPE type]` 实现 `MultiReadCommand`，通过数据库遍历接口直接访问候选项，不构建全库键列表或克隆 value。游标按键哈希的逻辑桶进行位反转遍历；每次完整扫描选中桶的二次探测序列，并覆盖正在迁移的后继表对应桶，因此扩缩容、同容量重建及其他键的增删不会漏掉完整扫描期间始终存在的键。迁移时允许重复键。COUNT 默认 10，在过期、MATCH、TYPE 过滤之前计数；每批最多选择 `10 * COUNT` 个根表逻辑桶，碰撞组不拆分，允许超出 COUNT 或返回空结果和非零游标。过滤使用固定读/写逻辑时钟，TYPE 与已有 TYPE 命令共用类型名称；未知类型合法但不匹配。

SCAN 不保存服务端会话、不增加第二份键索引或条目字段，也不让普通 GET/SET 额外加锁。扫描时重新计算候选键哈希，复制过的旧条目通过当前查询确认，因此扫描速度低于普通线性迭代；渐进迁移期间可能访问多张表。单表中每桶最多检查 `min(容量, 1 + 探测上限)` 个槽。前沿发现和复制条目的查询保留底层无锁但非 wait-free 的进展性质。普通快照仍使用原有无重复物理迭代器及版本/增量协议，不使用 SCAN。

Lua/EXEC 中返回全部匹配键的字节序排序结果及游标 0，避免节点本地哈希布局影响后续写入，复杂度为 O(N + M log M)。普通读取不做全库排序。重启、安装快照或切换主节点后客户端需从游标 0 重新扫描。容器内存和常用操作的对照见 `cache_cat/examples/mocha_map_bench.rs`，算法与继承代码说明见 `cache_cat/src/mocha/map/README.md`。

空库（包括 FLUSHDB 后）直接返回游标 0。已分配的表不能仅凭并发分片计数为 0 判断为空：该提示会触发槽位验证，并对复制条目查询当前状态，防止短暂零计数造成漏键。此空表验证遍历已分配槽位，不受 COUNT 限制；成本局限于 SCAN，不增加普通读写的计数操作。验证记录及基准方法见 `docs/mocha_lock_optimization.md`。

扩容只保留渐进式模式，默认每批迁移 64 槽。等待复制或发布完成时，使用共享的按地址停车队列，表内只保留原子等待计数，移除了每表等待登记 Mutex 和两层 HashMap。无人等待时不访问队列锁。分配后继表仍由紧凑的 `parking_lot::Mutex<()>` 保护，避免并发帮助线程重复分配大表；普通查找和未遇到迁移的点写不取得这把锁。

### Hash

Hash 的字段容器使用 `ScanMap<Bytes, HashValue>`，外层保留 `Arc<Mutex<_>>`。条目连续存放，桶链保存条目索引和缓存的哈希值，不为每个字段单独分配节点。支持已有 Hash 命令所使用的查找、插入、删除、遍历、克隆和序列化 API；ZSET 的成员索引也复用 ScanMap（见下文），外层 mocha 保持原有容器。

桶数为 2 的幂，负载因子上限为 0.5，仅桶数组保持较低负载，不额外翻倍分配条目数组。采用带随机密钥的 `ahash::RandomState`；每个桶维护轻量哈希标记，在大多数未命中查询中避免访问条目数组。删除时同步更新标记，避免长期增删使过滤能力退化。扩容一次性重建桶链，不采用渐进式迁移。单个删除通过交换尾部条目保持存储紧凑，并修复桶链；普通遍历与字段数量成正比。扩容仍会持有该 Hash 的互斥锁，并可能延迟串行 Raft 写入。

ScanMap 和 ScanSet 通过 `with_removals` 批量接口在数据结构内部管理回收策略：先执行传入的修改，只有成员数净减少且结果非空，才在结束时检查一次容量；命令实现不访问缩容阈值，也不调用缩容方法。HDEL、SREM、SPOP、ZREM、ZPOPMIN 用该接口包住整批删除循环，SINTERSTORE/SDIFFSTORE 则包住初始目标集合的全部过滤。ScanMap 分别判断条目数组容量和桶数组可容纳的有效成员容量：成员数必须严格低于对应容量的 10%，且每个待缩缓冲区预计至少回收 64 KiB。条目目标容量为当前成员数的两倍并向上取 2 的幂；桶目标按原有负载上限提供相应的成员余量，避免缩容后立即扩容。底层逐成员删除、普通读取、插入、未删除成员的操作和 clear 不触发检查。共用缩容逻辑保留稠密顺序和哈希种子，移动条目不克隆其内容，重建桶链使用缓存哈希。位反转扫描可跨越这种 2 的幂缩桶，允许重复但不漏掉完整扫描期间持续存在的成员。缩容在已有 value 锁和 Raft 串行应用期间同步执行 O(N) 工作，因此触发缩容的删除可能产生延迟尖峰。容量仍是节点本地信息，各节点缩容时机不同也必须产生相同的采样和枚举结果。

Redis Hash 写命令将稠密字段数组的顺序作为复制状态：新字段按参数顺序追加，更新保留位置，HDEL 将尾字段交换到删除位置。克隆、重建桶索引以及快照序列化和恢复均保留字段顺序，哈希种子和桶布局仍属于节点本地信息。Hash 命令不使用 ScanMap 中顺序依赖容量的通用 retain；未来新增过滤写入必须确保各副本字段顺序一致。HGETALL、HKEYS、HVALS 在普通读取和 Lua/EXEC 中均直接遍历稠密字段数组，复杂度 O(N)，无需排序；字段和值保持对应，HVALS 保留重复值。

HRANDFIELD 直接按字段数组下标读取，与 SRANDMEMBER 共用只读下标采样。单个采样为 O(1)，不创建辅助集合；正 count 返回不重复字段，k 截断到字段数量后，预期时间为 O(k)：少量采样使用稀疏的虚拟 Fisher-Yates 映射，较多采样使用长度不超过 4k 的临时下标数组，请求全部字段时直接返回稠密顺序。负 count 有放回采样，复杂度 O(abs(count))，只复制返回的字段和值。普通请求使用线程本地随机源，Lua/EXEC 根据复制的逻辑时钟和 key 初始化固定算法的随机数生成器。采样（包括 WITHVALUES）不修改字段顺序、值、TTL 或快照版本。

`HSCAN key cursor [MATCH pattern] [COUNT count] [NOVALUES]` 通过 `ReadCommand` 执行。普通请求采用位反转游标，完整扫描每个选中的桶，因此扩容和其他字段的增删不会漏掉完整扫描期间始终存在的字段。`COUNT` 默认 10，是扫描工作量提示，计数发生在 `MATCH` 过滤之前；每批最多尝试 `10 * COUNT` 个桶，碰撞链不拆分，所以允许超出 COUNT，也允许空结果携带非零游标。游标为 0 表示开始或结束，不保存服务端会话状态。

Raft 中 Lua/EXEC 的扫描结果可能决定后续写入。由于各副本的随机种子和容量不同，该路径返回匹配字段的完整排序结果和游标 0，允许接受普通扫描产生的游标，并可能重复返回先前已经扫描的字段。该路径时间开销为 O(N + M log M)，N 为字段总数、M 为匹配数；普通 HSCAN 不做整表排序。快照仅序列化字段和值，恢复时重建索引和随机种子；普通游标不保证跨重启、快照安装或主节点切换继续有效，此时客户端应从 0 重新扫描。

`MEMORY USAGE` 按实际桶数组和条目数组的容量估算容器内存。`cache_cat/examples/hash_map_bench.rs` 提供与原标准 HashMap 的查找、更新、删除、插入和遍历对照测试。

### List

使用 `std::collections::LinkedList` 实现。读写并发可以用crossbeam SegQueue实现。

### Set

Set 使用 `ScanSet<Bytes>`，在 ScanMap 上提供集合接口，值为零大小的 `()`，外层保留 `Arc<Mutex<_>>`。Set 在编译期选择最高 0.75 的桶负载，Hash/ZSET 保持原有 0.5 配置。增删、成员查询、稠密遍历和桶游标复用 ScanMap；Set 的 `retain` 无论本地容量如何，均按相同顺序交换尾部条目删除：稠密表在过滤后原地重建桶链，稀疏表逐项修复删除以避免遍历大量空桶。两种路径均复用缓存哈希，不分配临时集合，并在异常退出时保持索引有效。Hash/ZSET 保留已有过滤行为。集合运算的写入目标直接构建 ScanSet；纯读 SINTER/SDIFF 使用成员数组过滤，避免复制和维护临时桶索引。

稠密成员数组的顺序属于 Set 的复制状态。新成员按命令参数顺序追加，已有成员保持位置，删除时将尾成员移到被删除的位置。集合运算按源键参数顺序和源成员数组顺序构建结果，过滤后的顺序不能依赖节点本地哈希种子或容量。重建桶索引和快照克隆均保留成员顺序；全量快照和已计算的目标键写入按此顺序序列化成员，恢复时按相同顺序插入。哈希种子、缓存哈希、桶链和分配容量仍是节点本地信息，由恢复端重建。

`SPOP` 实现 `ComputeCommand`，使用 key 和随日志复制的写逻辑时钟初始化已有确定性随机数生成器，直接对稠密成员数组采样。按采样下标交换尾成员删除，并用缓存哈希修复桶链，无需收集或排序整个集合。返回 k 个成员时，采样的预期时间为 O(k)，响应空间为 O(k)；哈希碰撞仍保留通常的最坏情况限制。触发稀疏缩容的批次会额外对幸存成员执行 O(N) 工作。不新增成员字段、索引或锁。快照 `Start` 阶段写入前已有的整容器克隆仍有 O(N) 成本。复制测试需要比较成员数组顺序和后续 SPOP 响应（包括快照恢复后），不能仅比较集合成员是否相同。

SMEMBERS 在普通读取和 Lua/EXEC 中均直接按稠密成员顺序返回，复杂度 O(N)，无需排序。SRANDMEMBER 与 HRANDFIELD 共用只读下标采样：单成员为 O(1)，正 count 截断到集合大小后预期为 O(k)，允许重复的负 count 为 O(abs(count))；少量采样不构建全量成员数组。普通请求使用线程本地随机源，复制读取用 key 和逻辑时钟初始化固定算法的随机数生成器。采样只使用临时下标映射，不修改 Set 或成员顺序。这五个读取命令（SMEMBERS、SRANDMEMBER、HRANDFIELD、HGETALL、HVALS）的确定性依赖一致的修改历史和保留的数组顺序，不要求本地哈希布局相同，也不需要按字节排序响应。

`SSCAN key cursor [MATCH pattern] [COUNT count]` 使用 `ReadCommand`。普通读取采用位反转桶游标，COUNT 默认 10，在 MATCH 过滤前计数，每次最多尝试 `10 * COUNT` 个桶，碰撞链不拆分。允许超出 COUNT，也允许空结果携带非零游标。扩容以及其他成员的增删不会遗漏完整扫描期间始终存在的成员；RESP2/RESP3 均返回 `[cursor, [member, ...]]` 数组。

Lua/EXEC 中返回按成员字节排序的全部匹配成员和游标 0，避免副本本地哈希种子及容量不同影响后续写入。该路径开销为 O(N + M log M)，普通读取不执行全量排序。快照期间的容器克隆保留哈希种子，并为下一次写入保留适量条目容量，避免克隆后单成员 SADD 再次搬移整张表。桶数超过成员数八倍时，克隆按缓存哈希重建较小的桶数组。位反转游标支持同步扩缩容：缩容允许重复返回已扫描成员，但不会遗漏完整扫描期间始终存在的成员；快照仅持久化成员序列，恢复时重新建表，重启、快照安装或主节点切换后客户端应从 0 重新扫描。

`MEMORY USAGE` 按实际桶和条目数组容量估算。Set 的桶负载上限为 0.75，每个条目及桶也有额外索引元数据，`()` 零大小不表示容器成本与标准 HashSet 相同。同步扩容仍可能延迟串行 Raft 写入。`cache_cat/examples/set_bench.rs` 提供标准 HashSet 与 ScanSet 的常用读写、遍历、retain、克隆、克隆后写入和内存对照。基准支持基数、操作和成员长度筛选，以固定样本内哈希种子、交替运行顺序及最小累计计时降低噪声；结果为容器微基准，不代表完整 Raft 请求延迟。

### Sorted Set

ZSET 使用按 `(score, member)` 排序的带排名索引跳表，加上 `ScanMap<Bytes, f64>` 哈希索引，支持成员查找和游标扫描。每个跳表节点保存一小块有序成员，减少依赖访存和内存分配；每层链接维护按成员数计算的跨度，底层维护反向链接。节点使用稳定的 arena 索引并复用删除后的槽位，最多 32 层，逐层晋升概率为 1/4。块满时分裂，删除后空间允许时合并相邻块；分数更新未移出原块时复用已有分配。两个索引仍由现有 value 互斥锁保护，无需新增锁。

`ZRANK`、`ZREVRANK`、`ZCOUNT` 的期望时间复杂度为 O(log N)。按排名和分数的范围查询通过跨度定位边界，再遍历返回成员，期望为 O(log N + M)，包含反向查询和大 LIMIT 偏移。BYLEX 在所有成员同分这一 Redis 定义的场景下也通过索引定位；混合分数时保留原来的确定性过滤行为，可能全量遍历。成员查找仍为期望 O(1)，插入和删除为期望 O(log N)。

`ZSCAN key cursor [MATCH pattern] [COUNT count]` 使用 `ReadCommand`，基于哈希索引的位反转桶游标扫描。COUNT 默认 10，是 MATCH 过滤前的工作量提示；碰撞链保持完整，允许空结果携带非零游标。普通扫描不遍历或排序整个集合。扩容、其他成员的增删以及分数更新不会漏掉完整扫描期间始终存在的成员。响应包含游标和交替排列的成员、分数数组；RESP2 和 RESP3 的分数均使用 bulk string。

Raft 中执行的读取（Lua/EXEC）返回按成员字节排序的全部匹配项和游标 0，避免本地哈希种子、容量、跳表形状影响后续写入。此路径开销为 O(N + M log M)，普通读取不承担该成本。与 HSCAN 相同，重启、快照安装或主节点切换后，普通扫描应从游标 0 重新开始。

快照按分数、成员顺序仅序列化一次逻辑 `(member, score)`。恢复时逐条验证该顺序。对于编码声明超过 4096 个成员的集合，通过有界缓冲按顺序直接构建层链接、成员跨度和反向链接，并重建成员哈希索引，预期时间为 O(N)。构建保留普通顺序插入的布局：缓冲达到 65 个成员时，将前 32 个形成节点，其余继续作为尾部；完整节点及尾部沿用原来的预留容量，避免恢复后插入或合并增加重新分配。较小集合及未提供长度的编码保留逐项插入路径。初始预分配受限；恢复拒绝重复成员、NaN 分数及不符合分数、成员顺序的编码，正负零视为相同分数。这替换了之前 alpha 版本的 ZSET 编码。MEMORY USAGE 按哈希数组、跳表 arena 和层数组的实际分配估算内存，共享的成员 payload 只计算一次。`cache_cat/examples/zset_bench.rs` 对照原 BTreeSet + HashMap 实现测量查询及写入性能。 `cache_cat/examples/zset_restore_bench.rs` 测量快照解码和恢复后的读写性能。

分数等 double 回复的文本由 `format_double` 生成，对应 Redis 的 `d2string`：`nan`、`inf`/`-inf`、`0`/`-0` 为固定写法；绝对值不超过 2^62 的整数值按整数输出；其余交给 `cache_cat/src/utils/fpconv.rs`，它逐步移植了 Redis 使用的 `fpconv_dtoa`（Grisu2，Boost 许可证，文件头保留了原始声明）。没有使用 Rust 自带的最短表示，原因有两个。其一是写法不同：小于 0.001 且末位有效数字超出小数点后 6 位的值，以及有效数字之后还要补 8 个及以上零的大数，`fpconv_dtoa` 使用科学计数法（`1.2345e-4`、`1e+21`），而 `0.000015`、`10000000` 仍是普通写法。其二是 Grisu2 输出的并不总是最短数字串，例如恰好落在两个 double 中点上的十进制数（`1.726839e20` 输出为 `172683900000000020000`）。两者都会让回复的字节与 Redis 不同。ZSCORE、ZINCRBY、WITHSCORES、GEOPOS 以及 Lua 返回的 `{double=...}` 都经过这条路径；ZSCAN 的分数按 Redis 的 `%.17Lg` 单独处理。

### Geospatial

GEO 索引就是普通的 ZSET：成员的分数是经纬度按 Redis `geohash.c` 交织得到的 52 位整数（经度 ±180、纬度 ±85.05112878，各 26 位），double 可以精确保存。不新增 `ValueObject`、快照编码或锁；`TYPE` 返回 `zset`，ZSET 命令和 GEO 命令可以读写同一个键，删除成员使用 `ZREM`。命令实现位于 `cache_cat/src/protocol/geo`，编解码只使用加减乘除和整数转换，各平台结果逐位一致。

`GEOADD key [NX|XX] [CH] longitude latitude member [...]` 使用 `ComputeCommand`，对应独立的 Raft 指令 `BaseOperation::GeoAdd`。主节点在解析阶段完成全部校验并算出分数，日志只携带成员和分数；状态机应用时与 ZADD 共用同一段有序集合更新逻辑（Redis 同样把 GEOADD 改写为 ZADD 执行），不做浮点运算。参数不是完整的三元组、或同时给出 NX 和 XX 时返回语法错误；任何一对坐标非法都会拒绝整条命令，不写入任何成员。坐标按 Redis `string2d` 的规则解析：接受十六进制浮点和显式的无穷大，拒绝 NaN、上溢以及下溢为零的输入。快照 `Start` 期间 GEOADD 以自身记录到增量队列并按 CAS 回放，EXEC 和 Lua 中同样可用。

`GEOHASH key [member ...]` 使用 `ReadCommand`，返回每个成员的 11 字符标准 geohash，键或成员不存在时对应位置返回空值。内部分数使用的纬度范围比标准 geohash 窄，因此先解码为格子中心，再按 ±90 纬度重新编码；52 位只够 10 个字符，第 11 个字符与 Redis 一样固定为 `0`。持有 value 锁期间只查找成员分数，字符串在锁外生成。该命令也接受由 ZADD 写入的任意分数；超出 u64 范围的分数在 C 中转换结果未定义，这里采用饱和转换。

`GEOPOS key [member ...]` 使用 `ReadCommand`，对应读指令 `ReadOperation::GeoPos`，按参数顺序返回每个成员的经度和纬度。返回的是成员所在格子的中心，不是 GEOADD 收到的原始坐标，误差不超过一个格子（经度方向 360/2^26 度）；落在范围之外的中心会被钳制到坐标上下限。坐标的写法跟随 Redis 8.0 起使用的 `addReplyDouble`：RESP2 为批量字符串，RESP3 为 double，文本取能够往返的最短十进制表示，整数值不带小数部分；Redis 7.4 及更早版本则固定输出 17 位小数（如 `13.36138933897018433`）。键或成员不存在时对应位置是空数组（RESP2 为 `*-1`，RESP3 为 `_`），这一点与 GEOHASH 返回的空批量字符串不同。与 GEOHASH 相同，持有 value 锁期间只查找成员分数，解码在锁外进行，也接受由 ZADD 写入的任意分数；两个命令共用参数解析和分数查找。坐标文本由全局共用的 `format_double` 生成，因此靠近 0 的坐标与 Redis 一样写成科学计数法（如 `9.924173355102539e-5`）。

`GEODIST key member1 member2 [M|KM|FT|MI]` 使用 `ReadCommand`，对应读指令 `ReadOperation::GeoDist`，返回两个成员之间的距离。距离在两个成员所在格子的中心之间测量（即 GEOPOS 返回的位置），按 Redis `geohashGetDistance` 的 haversine 公式计算，地球视为半径 6372797.560856 米的球体；两点经度相同时与 Redis 一样直接按纬度差计算。单位省略时为米，名称不区分大小写，`km`、`ft`、`mi` 分别按 1000、0.3048、1609.34 米换算。回复在 RESP2 和 RESP3 中都是批量字符串，固定 4 位小数，对应 Redis 的 `fixedpoint_d2string`：先乘以 10000，再把得到的 double 按“五成双”取整，因此个别值与对精确十进制值舍入的 `%.4f` 不同（如 0.12345 输出 `0.1234`）。键不存在或任一成员不存在时返回空值；参数少于 4 个返回参数个数错误，单位非法返回 `ERR unsupported unit provided. please use M, KM, FT, MI`，单位之后还有参数返回语法错误，这些都在解析阶段判定，先于键的查找和类型检查。时间复杂度为 O(1)：持有 value 锁期间只做两次成员分数查找，解码和三角函数运算在锁外进行。单位解析、距离计算和回复格式位于 `cache_cat/src/protocol/geo/distance.rs`，供后续按距离查询的 GEO 命令复用。

距离计算中的 `sin`、`cos`、`asin` 来自纯 Rust 的 `libm` crate，而不是 `f64` 的同名方法。后者调用所在平台的 C 数学库，Rust 文档说明其结果随平台和版本而变；而 Lua/EXEC 中的 GEODIST 在每个副本上各自执行，脚本可以把读到的距离写回状态机，所以各副本必须得到逐位相同的结果。平方根由 IEEE 754 规定为正确舍入，仍使用 `f64::sqrt`。Redis 自身使用平台的 C 数学库，因此最后一位上并不存在唯一的“Redis 结果”。在 macOS ARM64 上用 700 万对坐标对照系统数学库：随机坐标对的差异都小于 1e-6 米，4 位小数的回复约百万分之五不同；haversine 公式在对跖点附近是病态的，互为对跖点的坐标对中约 3% 相差可达 0.19 米。

`GEORADIUS key longitude latitude radius M|KM|FT|MI [WITHCOORD] [WITHDIST] [WITHHASH] [COUNT count [ANY]] [ASC|DESC] [STORE key|STOREDIST key]` 返回某个位置给定半径内的成员。不带 STORE 或 STOREDIST 时它只读，因此使用 `ReadCommand`，对应读指令 `ReadOperation::GeoRadius`，走租约读而不写日志，尽管 Redis 把这个命令标记为写命令。带 STORE 或 STOREDIST 时使用 `MultiReadComputeCommand`，对应写指令 `RedisOperation::RedisGeoRadiusStore`：读取源键，把找到的成员作为一个有序集合写入目标键，分数是成员的 geohash（STORE），或者是以半径单位表示、未经舍入的距离（STOREDIST）。目标键无论原来是什么类型都会被替换并失去 TTL；没有找到成员或源键不存在时目标键被删除，回复是写入的成员数。快照 `Start` 阶段只记录计算出的目标键写入，回放时不会再去搜索可能已经变化的源键。两种形式都可以在 EXEC 和 Lua 中使用。

搜索逻辑位于 `cache_cat/src/protocol/geo/search.rs`，供其他按距离查询的命令复用，并且逐步对照 Redis 的 `geohash_helper.c` 和 `geo.c`：先由半径和圆心纬度估算格子大小，取圆心所在的格子及其周围八个邻格；如果某个邻格够不到圆的外接矩形的边，就把格子放大一级；圆心格子在某一侧已经容纳整个矩形时，去掉那一侧的邻格。然后按“中心、北、南、东、西、东北、西北、东南、西南”的顺序扫描每个格子的分数范围，成员所在格子的中心（即 GEOPOS 返回的位置）到圆心的距离（即 GEODIST 的算法）不超过半径时保留。这个扫描顺序就是不带 ASC/DESC 时的回复顺序，也决定了 `COUNT n ANY` 在哪些成员处停止，因此实现保留了 Redis 的细节，包括：网格在四条边上都是回绕的；与上一个扫描过的格子相同的格子会被跳过，全球范围的搜索才不会把成员返回两次；GEOADD 写在经度恰为 180 或纬度恰为 85.05112878 处的成员，其格子编号比网格大一，只有以该上限为圆心的搜索才能找到。外接矩形需要一次 `cos`，与距离计算一样取自 `libm`，所以各副本扫描的格子相同。

只有 COUNT 而没有 ANY 时按距离排序，默认由近到远，指定 DESC 时由远到近。ANY 返回扫描最先找到的成员，指定了顺序时只对这些成员排序。Redis 用 `qsort` 排序，COUNT 截断结果时用部分排序，两者都没有规定距离相等的成员（例如同一个格子里的两个成员）的先后；这里它们在两个方向上都保持扫描顺序。结果很多而 COUNT 很小时先选出前 count 个再排序，复杂度为 O(N + count log count)。没有 ANY 时，持有 value 锁期间只复制候选成员和分数，解码和三角函数运算在锁外进行，所以对同一个热点索引的搜索可以并行，对 Raft apply 线程的阻塞也只有复制这一段。ANY 需要在找到足够的成员时立刻停止，因此在锁内计算距离。

回复的每一项是成员本身；带 WITH 选项时是一个数组，成员之后依次为距离（WITHDIST，与 GEODIST 相同的 4 位小数字符串，单位同半径）、整数形式的分数（WITHHASH）和坐标（WITHCOORD，写法同 GEOPOS），这个顺序与选项的书写顺序无关。键不存在或没有结果时返回空数组。Redis 在读取任何参数之前先查找键并检查类型，所以解析阶段只拒绝参数个数错误：其余参数错误虽然在解析时判定，但随读指令带到执行阶段，确认键不是其他类型之后才返回。在 MULTI 中也因此与 Redis 一致：参数个数错误在入队时被拒绝并使事务中止，其余参数错误是该命令在 EXEC 结果中的回复。按 Redis 的检查顺序，错误依次为：坐标非法、`ERR need numeric radius`、`ERR radius cannot be negative`、单位非法；然后从左到右读取选项，遇到语法错误、COUNT 不是整数或 `ERR COUNT must be > 0`；最后是 STORE 与 WITH 选项同时出现，以及 ANY 没有 COUNT。需要取值的选项出现在最后一个参数时是语法错误，重复的选项以后一个为准。

`GEORADIUSBYMEMBER key member radius M|KM|FT|MI [WITHCOORD] [WITHDIST] [WITHHASH] [COUNT count [ANY]] [ASC|DESC] [STORE key|STOREDIST key]` 是以索引中某个成员的位置为圆心的 GEORADIUS，选项和回复都相同；成员自身也在结果中，距离为 0。它有自己的指令：读指令 `ReadOperation::GeoRadiusByMember`，带 STORE 或 STOREDIST 时是写指令 `RedisOperation::RedisGeoRadiusByMemberStore`。圆心取成员所在格子的中心，也就是 GEOPOS 返回的位置，因此回复与在该位置上执行 GEORADIUS 逐字节相同。成员的查找和周围格子的扫描在同一次持锁期间完成，圆心和找到的成员来自索引的同一个状态；距离计算与 GEORADIUS 一样在锁外进行。

Redis 读取这个命令的参数的顺序取决于键是否存在，这里的实现与之一致。首先检查键的类型。只有键存在时才查找成员（索引中没有该成员时返回 `ERR could not decode requested zset member`），然后读取半径和单位。选项最后读取。键不存在时，成员、半径和单位完全不会被读取：即使它们非法，回复也是空数组，带 STORE 时目标键照样被删除。因此半径和选项的错误都在解析阶段判定、随指令携带，到 Redis 会读取该参数的位置才返回。写指令在 `RedisOperation` 中是装箱的：它带有三个键，比其他所有请求都大，不装箱会撑大每个命令都要携带的 `Operation`。圆心之后的参数、回复以及 STORE 的写入与 GEORADIUS 共用，位于 `cache_cat/src/protocol/geo/radius.rs`。

其余 GEO 命令（GEOSEARCH、GEOSEARCHSTORE、GEORADIUS_RO、GEORADIUSBYMEMBER_RO）尚未实现。

### JSON

JSON 使用 `Arc<Mutex<JsonDocument>>`，内部直接存放 Redis 官方 `ijson` fork 的紧凑 `IValue`，不常驻第二份 JSON 文本或 `serde_json::Value`。上游版本和本地适配记录在 `vendor/ijson/UPSTREAM.md`。64 位平台的值句柄为 8 字节；短字符串内联，小对象按连续字段保存，同质数值数组使用紧凑元素。长字符串共享池在 JSON 内部同步，普通 Redis 类型不访问该池。

`JSON.GET key [INDENT indent] [NEWLINE newline] [SPACE space] [path ...]` 使用 `ReadCommand`。省略路径时采用 legacy 根路径 `.`；legacy 路径返回首个匹配值，`$` 路径返回匹配数组。多个路径返回以原路径为键的对象；混合 legacy 和 `$` 路径时，各项均为数组。格式化直接序列化借用的节点，不复制整份文档。`NOESCAPE` 为兼容选项，不关闭转义；RESP3 支持 `FORMAT STRING|EXPAND|EXPAND1`。

`JSON.TYPE key [path]` 使用 `ReadCommand`。省略路径时返回根节点类型。传统路径以批量字符串返回首个匹配节点的类型，没有匹配时返回 nil。JSONPath 按匹配顺序返回类型数组，没有匹配时返回空数组。两种模式下，键不存在都返回 nil。RESP3 会在成功回复外再包一层数组。JSON 空值的类型名为 `null`，整数为 `integer`，浮点数为 `number`。

`JSON.SET key path json [NX|XX]` 使用 `ComputeCommand`，日志保存输入字节和选项，状态机直接解析为紧凑树。只允许在根路径创建新 key；局部更新可创建已有对象的最后一级字段，不自动补齐中间容器。已有 key 的 TTL 在根替换和局部更新后均保留。支持 `FORMAT JSON|STRING|BSON` 和显式的 `FPHA` 数值数组选项，默认不启用有损浮点精度。命令均可用于 EXEC 和 Lua。`TYPE`/`SCAN TYPE` 使用 Redis 的 `ReJSON-RL` 类型名称。

`JSON.NUMINCRBY key path number` 使用 `ComputeCommand` 并保留键的 TTL。先确定全部匹配位置，再按顺序递增，重复命中的位置会累加多次。RESP2 对传统路径返回最后一个数值结果，对现代路径返回 JSON 数组。RESP3 对两种路径都返回原生数值数组。数组回复中，非数值匹配项用 null 占位。若后续结果溢出，先前已成功的递增会保留。快照增量记录这次部分写入及其预期版本，使恢复后的各项只累加一次。

`JSON.DEL key [path]` 使用 `ComputeCommand`，返回被删除的值的数量，同样可用于 EXEC 和 Lua。省略路径、`$` 和 legacy `.` 都表示根，删除根即删除 key；key 不存在时返回 0 且不解析路径，路径之后的多余参数被忽略，均与 Redis 一致。legacy 路径和 `$` 路径一样删除全部匹配项；重复匹配只删除一次，已匹配节点内部的匹配随祖先一起删除，不重复计数。局部删除保留 TTL；如果本次删除使根容器变成空对象或空数组，则与 Redis 一样删除整个 key，原本就为空的文档不受影响。

删除顺序沿用 RedisJSON：同一数组内下标从高到低，前一次删除不会移动待删除的下标；同一对象内先按键名升序删除非数字键，再按数值降序删除数字键。ijson 删除字段时把末尾字段换入空位，因此删除顺序决定剩余字段的顺序。该顺序属于复制状态，各副本以及快照 CAS 回放必须得到相同的字段顺序。匹配、去重和排序只在 JSON.DEL 内进行，成本为 O(N + M log M)，N 为遍历的节点数、M 为匹配数；每次数组元素删除还需移动其后的元素。

`JSON.STRAPPEND key [path] json-string` 使用 `ComputeCommand` 并保留键的 TTL。省略路径时选择根节点。传统路径返回最后一个匹配字符串追加后的字节长度。JSONPath 返回数组，其中字符串对应字节长度，其他值对应 null。命令先确定全部匹配位置，再按顺序追加，重复匹配会多次追加。直接路径无需扫描整个文档，多匹配路径只做一次匹配遍历。每次追加的复制成本与原字符串及解码后缀的字节长度之和成正比。快照 CAS 按同样的匹配顺序回放。

快照编码采用显式类型标签，直接通过 serde/bincode 流式编码树及数值数组，不依赖 `IValue` 的 `deserialize_any`。恢复校验深度、类型和数值，并保留对象字段顺序及数值数组精度。快照 `Start` 期间沿用现有 `snapshot_clone` 隔离：对象和数组会深克隆，长字符串共享；本实现不宣称分块 COW，也不保证大文档频繁更新时的低峰值。`MEMORY USAGE` 统计可达分配，跨 key 共享字符串和全局共享池使其与实际 RSS 存在差异。

## 读写并发模型

在Redis中有一个核心的执行队列，dispatcher，所有的命令都通过单线程执行。但在raft中这是不合适的，读命令和写命令的延迟差距较大。读命令通常可以在租约期内直接返回，写命令则要经过一轮完整的共识算法。此外raft核心执行也是单线程的。
自然而然的，cache-cat使用读写并发的Hashmap。

Rust的moka库已经保证了每个单key操作是原子的。读读之间显然是不冲突的。写写之间是串行的，因此也不会产生原子性问题。（这里的写包括了删除操作）

|                 | 单key写（多次） | 多key写 | 单key读 | 多key读 |
| --------------- | --------------- | ------- | ------- | ------- |
| 单key读（多次） | √               | x       | √       | √       |
| 多key读         | x               | x       | √       | √       |

当多key读遇到了多次的单key的写。比如这里执行mget读k1和k2：读取k1->写入k1->写入k2->读取k2。导致原子性出现问题，多key写同理。

当单key读取遇到了多key写：写k1->读取k1->读取k2->写k2，这里就读取到了中间状态。

Cache-cat中使用read_lock和write_lock来优化这个问题。

|                 | read_lock（RwLock） | write_lock（Mutex） |
| --------------- | ------------------- | ------------------- |
| 单key读（多次） | 读锁                | x                   |
| 多key读         | 读锁                | √                   |
| 单key写（多次） | x                   | √                   |
| 多key写         | 写锁                | √                   |

由于多key的读写是绝对的少数操作，只有多key操作下才会需要上俩把锁。
