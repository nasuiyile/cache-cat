# Data Structure Design

## Data Structure Documentation

> For simplicity, Redis's basic data structures are used as headings. Most operations are still in the development adaptation phase.

### String

All outer key/value operations use `mocha::map::HashMap`; `mocha::Mocha` wraps it with logical clocks and timing-wheel expiration. The local concurrent table in `cache_cat/src/mocha/map` derives from Papaya 0.2.4. Production no longer depends on the Papaya crate; it remains a dev dependency for comparison benchmarks. Atomic publication, incremental resizing and Seize reclamation are retained, supporting serial Raft writes alongside concurrent reads, background expiration and lazy deletion.

`SCAN cursor [MATCH pattern] [COUNT count] [TYPE type]` implements `MultiReadCommand` through a database traversal hook, without materializing a database-wide input-key list or cloning values. A bit-reversed cursor visits logical home hash buckets, completing each selected bucket's quadratic probe sequence and corresponding buckets in migration successors. Growth, shrinking, same-size rehashing and changes to other keys do not omit keys present throughout an iteration. Migration may produce duplicates. COUNT defaults to 10, counts candidates before expiration/MATCH/TYPE filtering, and limits each page to `10 * COUNT` root logical buckets. Collision groups are never split, so replies may exceed COUNT or be empty with a nonzero cursor. Filtering fixes read/write clocks for each call; TYPE shares the existing TYPE command's names, and unknown type names legally match nothing.

SCAN keeps no server-side sessions, extra key index or per-entry fields and adds no locks to ordinary GET/SET. It recomputes candidate hashes and resolves copied entries through current lookups, so it is slower than ordinary linear iteration; migration may require visiting several tables. In one table, each bucket examines at most `min(capacity, 1 + probe_limit)` slots. Frontier discovery and copied-entry lookups retain the underlying lock-free, not wait-free, progress qualification. Snapshots continue to use the original duplicate-free physical iterator and revision/delta protocol, not SCAN.

Lua/EXEC returns all matching keys sorted by bytes with cursor 0, avoiding replica-local hash layout influencing subsequent writes. This costs O(N + M log M); ordinary reads do not sort the database. Clients must restart at cursor 0 after restart, snapshot installation or leader changes. `cache_cat/examples/mocha_map_bench.rs` compares allocation bytes and common operations; `cache_cat/src/mocha/map/README.md` documents the algorithm and inherited code.

Empty databases, including after FLUSHDB, return cursor zero. For allocated tables, a zero sharded count only triggers verification: SCAN visits physical slots and validates copied entries against current state so transient counter values cannot omit stable keys. This exceptional emptiness check visits allocated slots and is not bounded by COUNT; it adds no counter operations to ordinary reads/writes. See `docs/mocha_lock_optimization.md` for validation and benchmark methodology.

Resizing is incremental only, with a default batch of 64 slots. Copy/promotion waiters use shared address-keyed parking queues; each table retains only an atomic pending count instead of a waiter-registry mutex and nested hash maps. No queue lock is touched when no one waits. A compact `parking_lot::Mutex<()>` still serializes successor allocation to prevent competing helpers allocating duplicate large tables; ordinary lookup and point writes outside migration do not take it.

### Hash

Redis Hash fields use `ScanMap<Bytes, HashValue>` inside the existing `Arc<Mutex<_>>`. Entries are dense; bucket chains store entry indices and cached hashes without allocating a node per field. It supports the lookup, insert, remove, iteration, clone and serde APIs used by existing Hash commands. ZSET also uses ScanMap for its member index, as described below; the outer mocha cache retains its existing map.

Bucket counts are powers of two, with a maximum load factor of 0.5; the lower load only enlarges the compact bucket array, not the dense entries allocation. The default keyed hasher is `ahash::RandomState`. Each bucket maintains a fingerprint bitset to reject most misses without reading entries. Removal refreshes the filter so churn cannot accumulate stale bits. Growth rebuilds all bucket chains synchronously; there is no incremental rehash. Individual removal swaps in the last entry and repairs its incoming bucket link, keeping ordinary iteration proportional to the number of fields. Growth holds the Hash mutex and can delay serial Raft writes.

ScanMap and ScanSet own sparse-storage policy through the `with_removals` batch interface. It runs the supplied mutations and checks capacity once after a net decrease in member count that leaves a nonempty container; command implementations do not access shrink thresholds or invoke shrink methods. HDEL, SREM, SPOP, ZREM and ZPOPMIN use this scope around the complete deletion loop, and SINTERSTORE/SDIFFSTORE around all filtering of the initial destination. ScanMap checks the entry allocation and the bucket array's effective member capacity independently: live count must be strictly below 10%, and each resized buffer must be expected to release at least 64 KiB. The entry target is twice the live count rounded up to a power of two; the bucket target provides that member headroom under the type's existing load limit. This hysteresis avoids immediately growing after shrink. Low-level per-member removal, ordinary reads, insertions, no-op deletions and clear do not trigger the check. The shared shrink operation preserves dense sequence and hash seed, moves entries without cloning their payloads, and rebuilds chains using cached hashes. Bit-reversed scans continue across power-of-two contraction with possible duplicates and no omission of members present throughout the scan. Shrink is synchronous O(N) work under the existing value lock and Raft apply serialization, so the triggering deletion may incur a latency spike. Capacity is local bookkeeping; nodes may shrink at different times while producing identical sampled and enumerated results.

Redis Hash writes preserve the dense field sequence as replicated state: new fields append in argument order, updates keep their positions, and HDEL swaps the last field into the deleted slot. Clone, rehash and snapshot serialization/restoration preserve this sequence while hash seeds and bucket layouts remain local. Hash commands do not use ScanMap's generic capacity-dependent retain; any future filtering write must preserve replica-identical field order. HGETALL, HKEYS and HVALS iterate the dense sequence directly in both ordinary reads and Lua/EXEC, taking O(N) without sorting. Fields and values remain paired in that sequence; HVALS retains duplicate values.

HRANDFIELD reads dense indices directly, sharing the read-only index sampler with SRANDMEMBER. A single sample needs O(1) time and no scratch collection. Positive counts return distinct fields in expected O(k) time, with k capped at cardinality: small subsets use a sparse virtual Fisher-Yates shuffle, larger subsets use a temporary index vector whose length is bounded by four times k, and requesting all fields returns dense order directly. Negative counts sample with replacement in O(abs(count)); only returned fields/values are copied. Ordinary calls use thread-local randomness; Lua/EXEC uses the replicated logical clock and key with the fixed deterministic RNG. Sampling never modifies the field sequence, values, TTL or snapshot revision, including WITHVALUES.

`HSCAN key cursor [MATCH pattern] [COUNT count] [NOVALUES]` implements `ReadCommand`. Ordinary reads use a bit-reversed cursor and visit entire buckets, preserving coverage of fields present throughout a full iteration despite growth and insertion/removal of other fields. COUNT defaults to 10 and is a work hint counted before MATCH filtering. A call visits at most `10 * COUNT` buckets, never splitting a collision chain: replies can exceed COUNT or contain no matches with a nonzero cursor. Zero starts or completes an iteration; there is no per-client scan state.

Lua/EXEC reads applied through Raft can affect subsequent writes. Since replicas have different local hash seeds and capacities, this path returns every matching field sorted by field bytes and cursor 0. It also accepts ordinary scan cursors and may repeat previously returned fields. Its cost is O(N + M log M), where N is the field count and M the matching count; ordinary HSCAN does not sort the whole hash. Snapshots serialize only fields and values, rebuilding indexes and randomized seeds on restore. Ordinary cursors are not guaranteed to survive restart, snapshot installation or leader changes; clients should restart at cursor 0 in those cases.

MEMORY USAGE accounts for the allocated entry and bucket arrays. `cache_cat/examples/hash_map_bench.rs` compares lookup, update, deletion, insertion and iteration against the former standard HashMap.

### List

Implemented using `std::collections::LinkedList`. For concurrent read and write, crossbeam's SegQueue can be used.

### Set

Sets use `ScanSet<Bytes>`, a set API over ScanMap with zero-sized `()` values, inside the existing `Arc<Mutex<_>>`. Sets select a maximum bucket load of 0.75 at compile time; Hash/ZSET retain the original 0.5 configuration. Insertions, removals, membership queries, dense iteration and bucket scans share ScanMap's implementation. Set `retain` uses the same swap-removal order regardless of local capacity: dense tables rebuild bucket links after filtering, while sparse tables repair individual deletions to avoid traversing empty buckets. Both paths reuse cached hashes, allocate no temporary collection and keep indexes valid during unwinding. Hash/ZSET retain their existing filtering behavior. Set store operations build their destination ScanSet directly; read-only SINTER/SDIFF filter member vectors without copying or maintaining a temporary bucket index.

The dense member sequence is part of replicated Set state. New members append in command argument order, existing members keep their position, and deletion moves the last member into the removed slot. Set algebra follows source-key order and source member sequences; filtering must produce the same sequence independently of local hash seeds or capacity. Rehashing and snapshot cloning preserve this sequence. Full snapshots and computed destination writes serialize it in order, and restoration inserts in that same order; hash seeds, cached hashes, bucket links and allocation capacities remain local and are rebuilt.

`SPOP` implements `ComputeCommand` and samples directly from this dense sequence using the existing deterministic RNG seeded by key and replicated write logical clock. Each sampled index is swap-removed using its cached hash to repair bucket links, without collecting or sorting the full set. For k returned members, sampling takes expected O(k) time and O(k) response storage; hash collisions retain the usual worst-case qualifications. A batch that triggers sparse shrink adds O(N) work on surviving members. There are no additional per-member fields, indexes or locks. During snapshot `Start`, the existing full-container clone before mutation still costs O(N). Replication tests compare member sequence and subsequent SPOP replies, including snapshot recovery, rather than only comparing set membership.

SMEMBERS returns this dense sequence directly in O(N), including Lua/EXEC, without sorting. SRANDMEMBER uses the same read-only index sampler as HRANDFIELD: O(1) for one member, expected O(k) for a positive count capped at cardinality, and O(abs(count)) for a negative count allowing duplicates. Small samples never materialize the full member array. Ordinary calls use thread-local randomness; replicated reads seed the fixed RNG from the key and logical clock. Sampling uses temporary index mappings only and leaves the Set and its order unchanged. These five reads (SMEMBERS, SRANDMEMBER, HRANDFIELD, HGETALL and HVALS) rely on equal mutation histories and preserved dense sequences, not equal local hash layouts or byte-sorted replies.

`SSCAN key cursor [MATCH pattern] [COUNT count]` implements `ReadCommand`. Ordinary reads use bit-reversed bucket cursors. COUNT defaults to 10 and counts entries before MATCH filtering; each call attempts at most `10 * COUNT` buckets without splitting collision chains. Replies may exceed COUNT or be empty with a nonzero cursor. Growth and insertion/removal of other members preserve coverage of members present throughout a full iteration. Both RESP2 and RESP3 return an array `[cursor, [member, ...]]`.

Lua/EXEC returns every matching member sorted by member bytes and cursor 0, avoiding replica-local hash seeds and capacities affecting later writes. This path costs O(N + M log M); ordinary reads do not sort the full set. Snapshot-time clones preserve hash seeds and bounded entry headroom so a subsequent single-member SADD does not move the entire entry array again. When buckets outnumber members by more than eight to one, clones rebuild a smaller bucket array using cached hashes. Bit-reversed cursors support synchronous growth and contraction: shrinking may repeat previously scanned members, but preserves coverage of members present throughout the iteration. Snapshots persist only member sequences and rebuild tables on restore; clients must restart at cursor 0 after restart, snapshot installation or leader changes.

MEMORY USAGE accounts for allocated bucket and entry arrays. The Set bucket load factor is at most 0.75 and entries/buckets carry index metadata: zero-sized `()` does not make its table cost equal to standard HashSet. Synchronous growth can still delay serial Raft writes. `cache_cat/examples/set_bench.rs` compares common reads/writes, iteration, retain, cloning, writes following cloning and table memory against standard HashSet. It supports operation/cardinality/member-width filters, fixed seeds within each sample, alternating run order and minimum accumulated timing to reduce noise. These are container microbenchmarks, not complete Raft request latency measurements.

### Sorted Set

ZSET uses an indexed skiplist ordered by `(score, member)` and a `ScanMap<Bytes, f64>` hash index for member lookup and cursor scans. Each skiplist node holds a small sorted block of members to reduce dependent memory accesses and allocations. Links carry spans measured in members, and level-zero backward links support reverse ranges. Nodes use stable arena indices and recycled slots, with at most 32 levels and a promotion probability of 1/4. Blocks split when full and merge with adjacent blocks when space permits; score updates staying within a block reuse its allocation. The existing per-value mutex protects both indexes; no additional locks are required.

`ZRANK`, `ZREVRANK`, and `ZCOUNT` take expected O(log N). Rank and score ranges seek their boundaries using spans and then visit the returned members, taking expected O(log N + M), including reverse ranges and large LIMIT offsets. BYLEX also uses indexed boundaries when all scores are equal, as required by Redis; mixed-score BYLEX retains deterministic filtering and may scan the whole set. Member lookup remains expected O(1), while insertions and removals take expected O(log N).

`ZSCAN key cursor [MATCH pattern] [COUNT count]` implements `ReadCommand` and uses the hash index's bit-reversed bucket cursor. COUNT defaults to 10 and is a work hint before MATCH filtering; complete collision chains are returned, and a page may be empty with a nonzero cursor. Ordinary scans do not traverse or sort the whole set. Members present throughout an iteration remain covered despite growth, other member insertions/removals, or score updates. Replies contain a cursor and a flat member/score array; scores are bulk strings under both RESP2 and RESP3.

For reads applied through Raft (Lua/EXEC), ZSCAN returns all matching members sorted by member bytes with cursor 0, independent of local hash seeds, capacity and skiplist layout. This path costs O(N + M log M); ordinary reads do not pay that cost. As with HSCAN, restart, snapshot installation and leader changes require restarting ordinary scans from cursor 0.

Snapshots serialize each logical `(member, score)` once in score/member order. Restoration validates that order. For sequences declaring more than 4096 members, a bounded buffer directly builds level links, member spans and backward links in order, while rebuilding the member hash index, in expected O(N) time. Construction preserves the ordinary sorted-insertion layout: at 65 buffered members, the first 32 form a node and the remainder stays in the tail. Nodes and the tail keep their usual spare capacity so subsequent insertions and merges need no extra reallocations. Smaller sets and encodings without a length hint retain per-member insertion. Initial preallocation is bounded; duplicate members, NaN scores and out-of-order entries are rejected, with signed zeros comparing as equal scores. This replaces the previous alpha ZSET encoding. MEMORY USAGE accounts for the hash arrays, skiplist arena and level allocations, counting shared member payloads once. `cache_cat/examples/zset_bench.rs` compares queries and writes against the former BTreeSet + HashMap implementation. `cache_cat/examples/zset_restore_bench.rs` measures snapshot decoding and reads/writes on the restored layout.

The text of scores and other double replies comes from `format_double`, which mirrors Redis `d2string`: `nan`, `inf`/`-inf` and `0`/`-0` are fixed, integral values up to 2^62 in magnitude are written as integers, and everything else goes to `cache_cat/src/utils/fpconv.rs`, a step-by-step port of the `fpconv_dtoa` Redis uses (Grisu2, Boost license, with the original notice kept in the file header). Rust's own shortest representation is not used for two reasons. First, the notation differs: for values below 0.001 whose last significant digit lies beyond the sixth decimal place, and for large values that need eight or more zeroes after their digits, `fpconv_dtoa` writes scientific notation (`1.2345e-4`, `1e+21`), while `0.000015` and `10000000` stay plain. Second, Grisu2 does not always produce the shortest digits, for example for a decimal that lies exactly halfway between two doubles (`1.726839e20` is written as `172683900000000020000`). Either difference would change the bytes of a reply. ZSCORE, ZINCRBY, WITHSCORES, GEOPOS and a `{double=...}` returned from Lua all take this path; ZSCAN formats its scores separately with Redis `%.17Lg`.

### Geospatial

A GEO index is an ordinary ZSET. A member's score is the 52-bit integer that Redis `geohash.c` interleaves from its longitude and latitude (±180 and ±85.05112878, 26 bits each), which a double stores exactly. There is no new `ValueObject`, snapshot encoding or lock; `TYPE` returns `zset`, ZSET and GEO commands read and write the same key, and members are removed with `ZREM`. The commands live in `cache_cat/src/protocol/geo`. Encoding and decoding use only `+ - * /` and integer conversions, so every platform produces the same bits.

`GEOADD key [NX|XX] [CH] longitude latitude member [...]` implements `ComputeCommand` and has its own Raft operation, `BaseOperation::GeoAdd`. The leader validates every argument and computes the scores while parsing, so the log carries only members and scores. Applying it shares the sorted-set update with ZADD (Redis also executes GEOADD by rewriting it to ZADD) and needs no floating-point arithmetic. Incomplete triples, or NX together with XX, are syntax errors. One invalid coordinate pair rejects the whole command without adding any member. Coordinates follow Redis `string2d`: hexadecimal floats and explicit infinities parse, while NaN, overflow and underflow to zero are rejected. During snapshot `Start`, GEOADD is queued as itself and replayed through CAS. It also works inside EXEC and Lua.

`GEOHASH key [member ...]` implements `ReadCommand` and returns the standard 11-character geohash of each member, with a null for a missing key or member. Scores cover a narrower latitude range than standard geohashes, so the score is decoded to the centre of its cell and encoded again for ±90 latitude. 52 bits fill only ten characters; as in Redis, the eleventh is always `0`. Only the score lookups run under the value lock, and the strings are built after it is released. The command also accepts arbitrary scores written by ZADD. Converting a score outside the u64 range is undefined in C; this implementation saturates.

`GEOPOS key [member ...]` implements `ReadCommand` with its own read operation, `ReadOperation::GeoPos`, and returns the longitude and latitude of each member in argument order. A position is the centre of the member's cell, not the pair GEOADD received, so it is off by at most one cell (360/2^26 degrees of longitude); a centre outside the valid range is clamped to the limits. Coordinates are written like the `addReplyDouble` that Redis uses here since 8.0: bulk strings in RESP2 and doubles in RESP3, as the shortest decimal that round-trips, with no fraction for integral values. Redis 7.4 and earlier printed 17 fractional digits instead (such as `13.36138933897018433`). A missing key or member is a null array (`*-1` in RESP2, `_` in RESP3), unlike the null bulk string GEOHASH returns. As with GEOHASH, only the score lookups run under the value lock, decoding happens after it is released, and arbitrary scores written by ZADD are accepted; the two commands share their argument parsing and score lookup. The text comes from the crate-wide `format_double`, so coordinates close to zero are written in scientific notation as in Redis (such as `9.924173355102539e-5`).

`GEODIST key member1 member2 [M|KM|FT|MI]` implements `ReadCommand` with its own read operation, `ReadOperation::GeoDist`, and returns the distance between two members. It is measured between the centres of the two members' cells (the positions GEOPOS returns) with the haversine formula of Redis `geohashGetDistance`, on a sphere with a radius of 6372797.560856 meters; when both longitudes are equal the distance is taken from the latitude difference alone, as in Redis. The unit defaults to meters, its name is case-insensitive, and `km`, `ft` and `mi` convert at 1000, 0.3048 and 1609.34 meters. The reply is a bulk string with four fractional digits in both RESP2 and RESP3, as written by Redis `fixedpoint_d2string`: the value is multiplied by 10000 and the resulting double is rounded half to even, so a few values differ from `%.4f`, which rounds the exact decimal value (0.12345 is written as `0.1234`). A missing key or member is a null. Fewer than four arguments are an arity error, an unknown unit is `ERR unsupported unit provided. please use M, KM, FT, MI`, and anything after the unit is a syntax error; all three are decided while parsing, before the key is looked up or its type is checked. The command is O(1): only the two score lookups run under the value lock, and decoding and trigonometry happen after it is released. Unit parsing, the distance and the reply format live in `cache_cat/src/protocol/geo/distance.rs` for the GEO commands that will search by distance.

`sin`, `cos` and `asin` come from the pure-Rust `libm` crate rather than from the `f64` methods. Those call the platform's C math library, and the Rust documentation states that their results vary by platform and version; a GEODIST inside Lua/EXEC runs on every replica and a script may write the distance it read, so all replicas have to produce the same bits. The square root is correctly rounded by IEEE 754 and still uses `f64::sqrt`. Redis itself uses the platform's C math library, so there is no single "Redis result" for the last digit. Compared with the system library on macOS ARM64 over seven million coordinate pairs, random pairs differ by less than 1e-6 meters and about five replies in a million differ in their four digits; the haversine formula is ill-conditioned near antipodes, where about 3% of exactly antipodal pairs differ by up to 0.19 meters.

`GEORADIUS key longitude latitude radius M|KM|FT|MI [WITHCOORD] [WITHDIST] [WITHHASH] [COUNT count [ANY]] [ASC|DESC] [STORE key|STOREDIST key]` returns the members within a radius of a position. Without STORE or STOREDIST it only reads, so it implements `ReadCommand` with its own read operation, `ReadOperation::GeoRadius`, and takes the lease-read path rather than the log, although Redis flags the command as a write. With STORE or STOREDIST it implements `MultiReadComputeCommand` with its own write operation, `RedisOperation::RedisGeoRadiusStore`: it reads the source and replaces the destination with a sorted set of the members found, scored by their geohash (STORE) or by their unrounded distance in the unit of the radius (STOREDIST). The destination is replaced whatever it held and loses its TTL; it is deleted when nothing is found or the source is missing, and the reply is the number of members stored. During snapshot `Start` only the computed write to the destination is recorded, so a replay never searches a source that has changed since. Both forms work inside EXEC and Lua.

The search lives in `cache_cat/src/protocol/geo/search.rs` for the other commands that query by distance, and follows Redis `geohash_helper.c` and `geo.c` step by step. The radius and the latitude of the centre choose a cell size. The cell of the centre and its eight neighbours are taken, one size larger if a neighbour does not reach the edge of the circle's bounding box, and the neighbours on a side where the centre cell already holds the box are dropped. The score range of each remaining cell is then scanned in the order centre, north, south, east, west, north-east, north-west, south-east, south-west, and a member is kept when the centre of its cell (the position GEOPOS returns) is within the radius by the distance GEODIST measures. That scan order is the order of a reply without ASC or DESC and decides which members `COUNT n ANY` stops at, so the port keeps the details of Redis, including these: the grid wraps around at all four edges; a cell equal to the one scanned last is skipped, which keeps a search of the whole globe from returning members twice; and a member GEOADD stored at exactly longitude 180 or latitude 85.05112878 has a cell number one past the grid and is found only by a search centred on that limit. The bounding box needs one `cos`, taken from `libm` like the trigonometry of the distance, so every replica scans the same cells.

COUNT without ANY sorts by distance, nearest first unless DESC is given. ANY returns the first members the scan finds, and sorts only those if an order is given. Redis sorts with `qsort`, or with a partial sort when COUNT cuts the result, and neither defines the order of members at equal distance, such as two members in one cell; here they keep the scan order in both directions. A small COUNT on a large result selects before it sorts, in O(N + count log count). Without ANY only the candidate members and scores are copied under the value lock, and decoding and trigonometry run after it is released, so searches of one hot index run in parallel and hold up the Raft apply thread only for the copy. ANY has to stop at the first matches and therefore measures under the lock.

Each entry of the reply is the member, or an array of the member followed by the distance (WITHDIST, the four-digit string of GEODIST in the unit of the radius), the score as an integer (WITHHASH) and the position (WITHCOORD, written like GEOPOS), in that order whatever the order of the options. A missing key or an empty result is an empty array. Redis looks the key up and checks its type before it reads any argument, so only the arity is rejected while parsing: every other argument error is decided while parsing, carried in the read operation, and sent once the key turns out not to hold another type. Inside MULTI this matches Redis as well: an arity error is rejected when the command is queued and aborts the transaction, and any other argument error is the reply of that command in EXEC. In the order Redis checks them, the errors are an invalid coordinate, `ERR need numeric radius`, `ERR radius cannot be negative`, an unsupported unit, then for the options from left to right a syntax error, a COUNT that is not an integer or `ERR COUNT must be > 0`, and finally STORE together with a WITH option and ANY without COUNT. An option that takes a value is a syntax error as the last argument, and a repeated option replaces the earlier one.

`GEORADIUSBYMEMBER key member radius M|KM|FT|MI [WITHCOORD] [WITHDIST] [WITHHASH] [COUNT count [ANY]] [ASC|DESC] [STORE key|STOREDIST key]` is GEORADIUS around the position of a member of the index, with the same options and replies; the member itself is among the results, at distance zero. It has its own operations: `ReadOperation::GeoRadiusByMember`, and with STORE or STOREDIST `RedisOperation::RedisGeoRadiusByMemberStore`. The centre is the centre of the member's cell, the position GEOPOS reports, so the reply equals that of GEORADIUS at that position byte for byte. The member is looked up and the cells around it are scanned under one hold of the value lock, so the centre and the members found come from the same state of the index; measuring still runs after the lock is released, as in GEORADIUS.

Redis reads the arguments of this command in an order that depends on the key, and so does this implementation. The type of the key comes first. Only if the key exists, the member is looked up (`ERR could not decode requested zset member` when the index does not hold it) and then the radius and its unit are read. The options come last. Without a key neither the member nor the radius nor the unit is read at all: the reply is an empty array even when they are invalid, and with STORE the destination is still deleted. The errors of the radius and of the options are therefore decided while parsing, carried in the operation, and sent at the point where Redis would read the argument. The write operation is boxed inside `RedisOperation`: with three keys it is larger than every other request and would otherwise enlarge the `Operation` that all commands carry. The arguments after the centre, the reply and the write of STORE are shared with GEORADIUS in `cache_cat/src/protocol/geo/radius.rs`.

The other GEO commands (GEOSEARCH, GEOSEARCHSTORE, GEORADIUS_RO and GEORADIUSBYMEMBER_RO) are not implemented yet.

### JSON

JSON uses `Arc<Mutex<JsonDocument>>` around the compact `IValue` from Redis's official `ijson` fork, without retaining a second JSON text or `serde_json::Value`. `vendor/ijson/UPSTREAM.md` records the upstream revision and local adaptations. On 64-bit platforms, value handles occupy eight bytes; short strings are inline, small objects use dense fields, and homogeneous numeric arrays use compact elements. Synchronization of the shared long-string pool is confined to JSON; other Redis types do not access it.

`JSON.GET key [INDENT indent] [NEWLINE newline] [SPACE space] [path ...]` implements `ReadCommand`. An omitted path means legacy root `.`. Legacy paths return their first match; `$` paths return match arrays. Multiple paths produce an object keyed by the original paths, with array-valued members whenever legacy and `$` paths are mixed. Replies serialize borrowed nodes without cloning the document. The compatibility option `NOESCAPE` does not disable escaping. RESP3 supports `FORMAT STRING|EXPAND|EXPAND1`.

`JSON.SET key path json [NX|XX]` implements `ComputeCommand`. Logs retain input bytes/options and apply parses directly into the compact tree. A new key can only be created at the root; a local update may add a final field to an existing object, without synthesizing intermediate containers. Both root replacement and local updates preserve an existing key's TTL. `FORMAT JSON|STRING|BSON` and explicit `FPHA` numeric-array options are supported; lossy float precision is not enabled by default. Both commands work inside EXEC and Lua. TYPE and SCAN TYPE use Redis's `ReJSON-RL` name.

`JSON.DEL key [path]` implements `ComputeCommand`, returns the number of deleted values, and also works inside EXEC and Lua. An omitted path, `$` and legacy `.` all mean the root, and deleting the root deletes the key. A missing key returns 0 without compiling the path, and arguments after the path are ignored, both as in Redis. Legacy paths delete every match just like `$` paths. A duplicate match is deleted once, and a match inside another matched node goes with its ancestor without being counted again. A partial deletion preserves the TTL. If the deletion leaves the root container as an empty object or array, the whole key is deleted as in Redis; a document that was already empty is unaffected.

Deletions follow RedisJSON's order. Within an array, higher indexes go first, so a removal never shifts a pending index. Within an object, non-numeric keys go first in ascending order, then numeric keys from the highest value down. ijson moves the last field into a removed slot, so this order decides the order of the remaining fields. That order is replicated state: every replica and snapshot CAS replay must produce the same field order. Matching, deduplication and sorting happen only inside JSON.DEL and cost O(N + M log M) for N visited nodes and M matches; removing an array element also shifts the elements after it.

Snapshots use explicit tags and stream the tree and typed numeric arrays through serde/bincode, without relying on `IValue`'s `deserialize_any`. Restoration validates depth, tags and numbers, preserving object order and numeric-array precision. During snapshot `Start`, the existing `snapshot_clone` isolation deep-copies objects and arrays while sharing long strings. This is not chunked COW and does not guarantee low peak memory under frequent large-document updates. MEMORY USAGE estimates reachable allocations; cross-key string sharing and the global pool mean this differs from process RSS.

### Others

It is known that Redis also supports bitmap, hyperloglog, Streams, Bitfield, etc. There are currently no plans to support them.

## Read-Write Concurrency Model

In Redis, there is a core execution queue, the dispatcher, and all commands are executed in a single thread. However, this is not suitable in Raft, as there is a significant latency gap between read and write commands. Read commands can typically return directly within the lease period, while write commands must go through a full round of the consensus algorithm. Additionally, the core Raft execution is also single-threaded.
Naturally, cache-cat uses a read-write concurrent Hashmap.

Rust's moka library ensures that each single-key operation is atomic. Read-read conflicts obviously do not occur. Write-write operations are serialized, so atomicity issues do not arise. (Write here includes delete operations)

|                 | Single-key Write (multiple) | Multi-key Write | Single-key Read | Multi-key Read |
| --------------- | --------------------------- | --------------- | --------------- | -------------- |
| Single-key Read (multiple)  | ✓                           | x               | ✓               | ✓              |
| Multi-key Read              | x                           | x               | ✓               | ✓              |

When a multi-key read encounters multiple single-key writes — for example, reading k1 and k2 via mget: read k1 -> write k1 -> write k2 -> read k2 — atomicity issues arise. The same applies to multi-key writes.

When a single-key read encounters a multi-key write: write k1 -> read k1 -> read k2 -> write k2 — an intermediate state is read.

Cache-cat uses read_lock and write_lock to optimize this issue.

|                 | read_lock (RwLock) | write_lock (Mutex) |
| --------------- | ------------------ | ------------------ |
| Single-key Read (multiple)  | Read lock          | x                  |
| Multi-key Read              | Read lock          | ✓                  |
| Single-key Write (multiple) | x                  | ✓                  |
| Multi-key Write             | Write lock         | ✓                  |

Since multi-key reads and writes are absolute minority operations, both locks only need to be acquired for multi-key operations.
